# 变更记录

## 2026-09-12

### 修复：认证时间戳超出 ±60s 窗口导致连接被拒（时钟偏差问题）

**现象**

服务端和客户端挂了两天后报错，第一天正常：

* 客户端：`WebTransport open failed (wt connect failed: server rejected WebTransport session request); falling back to HTTPS POST`、`server rejected authentication`
* 服务端 DEBUG 日志：收到 CONNECT 请求，bearer 时间戳与服务器当前时间相差 62 秒

**根因**

客户端机器的系统时钟比真实时间快约 62 秒，超出了认证的 ±60 秒时间窗（`AUTH_WINDOW`，`src/proto/crypto.rs`）。Bearer token 与带内 AUTH 帧中的时间戳均按本地时钟生成，服务端校验 `|now − ts| > 60` 时拒绝，表现为会话请求被 404。时钟偏差随时间缓慢漂移（第一天偶发失败、贴着窗口边缘，第二天彻底超窗 100% 被拒），与"挂了两天后报错"的时间线吻合。

### 修复：SNTP 单发易丢包，偶发 "deadline has elapsed"

Linux 服务端上 `clock sync ... failed: deadline has elapsed` 偶发出现：SNTP 是单次 UDP 交换、无重传，丢包或服务器繁忙时单次查询即失败（pool.ntp.org 每次还可能解析到不同服务器，稳定性进一步摊薄）。

修复：每轮同步最多尝试 3 次（间隔 2s），全部失败才告警并保留旧 offset；单次失败降级为 DEBUG 日志。



不再依赖系统时钟的准确性：进程内部维护一个 UTC 时钟，通过 SNTP 定期校准，认证时间戳全部改用它生成。

**实现**

* 新增 `src/clock.rs`：
  * 内置最小 SNTP 客户端（RFC 4330，48 字节 UDP 包），基于 tokio，不引入新依赖
  * 启动时立即同步一次，之后每 1 小时重新校准
  * `now = 系统时钟 + offset`，offset 由标准 NTP 公式 `((t2−t1)+(t2−t3))/2` 计算
  * 首次同步成功前 offset = 0（退化为系统时钟），同步失败不阻塞启动、保留旧 offset 并告警
  * 带 KoD（kiss-of-death）检测、reply mode 校验、5 秒超时
  * 每轮同步最多 3 次尝试（间隔 2s）：UDP 单发易丢包，单次失败自动重试
* `now_unix()`（`src/proto/crypto.rs`）改为走校准时钟，覆盖 Bearer token 与带内 AUTH 帧的时间戳
* 空闲超时用的 `now_millis()`（服务端本地相对时长）不受影响，仍用系统时钟

**CLI**

```
--time pool.ntp.org        # 默认（客户端+服务端均可用）
--time ntp.aliyun.com      # 自定义 NTP 服务器
--time 203.107.6.88:123    # 也支持 host:port
```

**验证**

* 实测 pool.ntp.org 与 203.107.6.88（阿里 NTP）：`clock synced with pool.ntp.org (offset -1s)`
* 修复过程中发现并解决两个实现 bug：
  1. `interval` 首个立即 tick 被预消耗，导致首次同步要等 1 小时
  2. SNTP 请求 T1 时间戳误用 NTP epoch（1970→1900 差 2,208,988,800 秒），导致 offset 计算错误；同时补上 T1（部分服务器拒绝不带 transmit timestamp 的请求）
* 全部 49 个测试通过，clippy 无警告

**部署**

两端重新构建部署即可。若客户端时钟偏差仍超过校准能力（SNTP 只算 offset，不改系统时间），程序内部时钟会自动补偿，无需手动对时。
