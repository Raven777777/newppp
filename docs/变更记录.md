# 变更记录

## 2026-09-14（P0 修复：`register()` 会话注册在 release 构建中被裁剪 + CI 新增 `cargo test --release`）

> 背景：`cargo test`（debug）90 项全绿，但 `cargo test --release` 有 **6 个失败**（`hub`/`state` 的配额与会话回收相关用例）。根因是一类隐蔽的编译裁剪 Bug。

### 修复（`src/server/state.rs:83` `ConnState::register`）

* **问题**：`try_register_with(sid, token)` 作为**条件表达式**写在 `debug_assert!(...)` 内。release 构建中 `debug_assert!` 的条件表达式被整体裁剪，副作用随之消失——**生产构建里会话从未注册**，导致：
  * 空闲会话回收（`reap_idle`）永远查不到多余的 registered handle，配额（`release_session`）不归还 → 全局 SESSION 池可被耗尽；
  * `drop_session` 返回 `false`，调用方跳过配额释放，DashMap `sessions` 无限增长。
* **修法**：无条件调用 `try_register_with`，仅对**返回结果**做 `debug_assert`（副作用移出断言）。debug/release 行为一致，失败语义仍由调用方兜底。

### 回归测试确认

* `cargo test --release`：修复前 6 failed → 修复后 **90 passed / 0 failed**（lib）+ 14 e2e passed；debug 下亦全绿。

### CI（`.github/workflows/ci.yml`）

* `check` job 新增 `cargo test --release --all-features`：这类"副作用藏在 `debug_assert!` 条件里"的裁剪 Bug 恰好 debug 绿、release 红，故 release 测试必须常驻 CI 防线（附注释说明动机）。

### 全项目审查结论（同日 Rust 审查）

* unsafe = 0 处；无 `#[allow]` 压制；`clippy --all-targets -D warnings` 零警告；`fmt --check` 干净；`cargo audit` 0 命中；`machete`/`miri` 未安装（环境不支持）。

## 2026-09-14（限速语义修正：`--rate` 改为按用户共享桶，覆盖双向 + UDP）

> 背景：原实现 `RateLimiter::new(st.rate_mbps)` 在**每次建连时各建一个桶**（`wt.rs` / `fallback.rs`），且只挂在「目标→客户端」下行泵上——多连接线性叠加配额、上行不限、UDP 不限，默认 `--rate 100` 实际允许远超 100 Mbps（实测多连接可跑满 1.3 Gbps）。

### 语义修正（`src/server/{state,wt,fallback}.rs`）

* **per-uid 共享桶**：`ServerState` 新增 `rates: DashMap<uid, Arc<RateLimiter>>` 与 `rate_for(uid)`（首用创建，全员共享）；`ConnState.rate` 改为 `Arc<RateLimiter>`。同一 uid 的全部连接（WT 主路径 + fallback 双承载）共同消耗一个桶，`--rate` 成为**每用户**配额而非每连接；
* **上行纳入限速**：client→target 方向（mux 泵 + 专用流 pump，`hub.rs`）在写出前 `acquire(n)`；
* **UDP 纳入限速**：`udp_feed` 发往目标、`spawn_udp_recv` 回包均按字节数计费。

### 测试与验证

* lib 87 → **90**（`rate_for_shares_one_bucket_per_uid`：同 uid 同桶 `Arc::ptr_eq`，异 uid 独立桶）；e2e 14 项全部通过；
* `cargo check --all-targets` / `clippy -D warnings` 零警告 / `fmt --check` 干净。

### 行为变化（收严）

* `--rate N` 现在是**每用户总带宽**：TCP 上/下行 + UDP 中转全计，多连接不叠加、多用户互不影响；
* 桶容量 = 1 秒的率值（短时突发最多预存 1s 的量），跨连接突发同样受限；
* 低速率（如 1）下限速严格生效，建议部署后实测校准。

## 2026-09-14（F-6 直连路径 SNI 伪装 + 证书 pinning：`--sni` / `--pin`）

> 方案变更：原 F-6「真实 ECH + DoH」废弃（运维链长：需 CF 配合 + DNS HTTPS RR 发布 + DoH 前置），改向 **SNI 伪装**——伪装域名不必是自己的域名，只需让 ISP 认为我们在访问某个它认识的域名；DNS 查伪装域名，实际连接自己的 IP。决策过程与取舍见 [待办_新.md](待办_新.md) F-6。

### 新增 CLI（`src/config.rs`，客户端 only）

* `--sni <域名>`：伪装 SNI——TLS ClientHello 的 SNI 与 DNS 查询目标都换成该域名，实际连接地址取自原始 URL 的 host:port。缺省 = 现行行为（SNI = URL host）；
* `--pin <指纹>`：SHA-256 证书指纹 pinning（64 hex，容忍 OpenSSL 冒号分隔格式）。设置后**完全替代 CA 校验**——服务器身份就是那枚证书，比公共 CA 校验更强（无签发链风险）。与 `--skip-verify` 互斥报错；
* 校验规则：`--sni` 必须 `--pin`（推荐）或 `--skip-verify`（伪装名下证书不可能匹配，身份必须显式锚定）；`--sni` + `wss://` 报错拒绝（CF 按真实 SNI 路由回源，伪装会断链）；主机名格式校验（长度/字符集）。

### 实现（`src/client/tls.rs` 新增；`src/client/{wt,fallback,outbound}.rs` 接线）

* **`PinVerifier`**：rustls `ServerCertVerifier` 实现——SHA-256(end_entity DER) == pin 指纹（恒时比较），签名验证仍走 provider 算法（握手密码学不变，仅替换信任锚决策）；
* **`FixedResolver`**：wtransport `DnsResolver` 实现——所有查询返回固定地址。WT 路径 `new_pool` 重写 URL host 为伪装名 + 挂 resolver（wtransport 的 resolver 只能在 config 阶段挂载）；
* **`HyperFixedResolver`**：hyper-util `Resolve`（sealed trait，经 `tower_service::Service<Name>` blanket 实现）。fallback POST 路径 `HttpConnector::new_with_resolver` 接入；非伪装模式走 `system_fallback()`（spawn_blocking getaddrinfo，与 GaiResolver 等价，统一 connector 泛型）；
* 两路径 TLS config 均在 pin 模式下保留 GREASE ECH（与 SNI 伪装正交）。

### 测试与验证

* lib 测试 78 → **87**（+9：config 校验 ×7、PinVerifier ×2）；
* e2e 11 → **13**（+2：`sni_masquerade_with_pin_connects`——伪装 SNI + 正确指纹对自签服务端完成 SOCKS5 CONNECT 往返；`sni_masquerade_wrong_pin_rejected`——错误指纹握手拒绝、会话不可建立）；
* `cargo fmt --check` 干净、`cargo clippy --all-targets` 零警告。

### 部署提示（详见待办 F-6 条目与手册）

* **指纹获取**：`openssl x509 -in cert.pem -noout -fingerprint -sha256`（服务器上执行），或客户端侧 `openssl s_client -connect host:443 | openssl x509 -noout -fingerprint -sha256`（对 TCP 端口有效；WT 与 fallback 共用同一张证书，指纹一致）。完整指南见 [手册.md](手册.md#pin-指纹获取与轮换)；
* **pin 的是握手对端的证书**：档位 1（nginx 终止 TLS）下 pin nginx 的证书；
* **轮换即失效**：换证书后客户端全部拒绝（`certificate fingerprint mismatch (--pin)`）——`--pin` 预期组合是自签/长有效期证书；LE 自动续期部署不要用 `--pin`/`--sni`；
* 伪装域名选型：境外热门 + 支持 h3/QUIC + 与 VPS 托管地区合理共存（境外 IP + 国内域名组合在交叉分析下反而可疑）；
* **最强形态是无域名部署**：VPS 不发布 A 记录 + URL 直接写 IP + `--pin` 唯一身份锚点——SNI-IP 交叉检查无从下手；
* 档位 1（nginx 终止 TLS）需加 catch-all default server（SNI 变化后原 server 块不匹配）；
* IP 锚点不动：被动 DNS 库仍知道 VPS IP 历史解析——本项是"去明文化"，不是隐身。

## 2026-09-14（F 系列指纹与隐蔽性落地：借鉴 Hysteria v2，客户端四项 + HPKE 后端）

> 依据：hysteria-master 源码调研（ChromeParrot / ZeroLengthConnectionIDGenerator / ECH / padding 工具箱）+ wtransport 0.7.2 / quinn-proto 0.11.17 / rustls 0.23.44 源码逐项探明。计划与结论见 [待办_新.md](待办_新.md) F-1~F-5。

### F-1 零长度源 CID + 8 字节初始 DCID（`src/client/wt.rs`）

* Chrome 的源 CID 长度为 **0**，quinn 默认发 8 字节随机 CID——每个 UDP 包头明文可辨；quinn 客户端 Initial 包的 DCID 默认 **20 字节**（`MAX_CID_SIZE`），Chrome 是 8 字节——首个数据报即显眼。
* 落地：`quic_endpoint_config_mut().cid_generator(RandomConnectionIdGenerator::new(0))` + `quic_config_mut().initial_dst_cid_provider(8 字节)`。两者均为 wtransport feature "quinn" 下的公开配置面，零 fork。

### F-2 传输参数对齐可设项（`src/quic_tune.rs`）

* `receive_window`（= `initial_max_data` TP）从 quinn 默认 `VarInt::MAX`（≈2^62，任何浏览器都不会发）改为 32MB；
* `mtu_discovery_config(None)` 关闭 DPLPMTUD（Chrome 默认不做 PMTUD；quinn 默认 600s 探测，探测包本身是链路特征）；
* quinn 默认已与 Chrome 一致的部分不动：`max_idle_timeout=30s`、streams 100/100、`ack_delay_exponent=3`、`max_ack_delay=25ms`、`max_udp_payload_size=1472`（探针核实：后四者因等于编码默认值**不上线**）；
* **残留已定性**（写入待办）：quinn 硬编码总是发送 `min_ack_delay` / `grease_transport_parameter` / `write_order`，无 setter 可关——TP 层无法消除的"我是 quinn"信号，消除需 fork quinn-proto（明确不做）。

### F-3 心跳去周期化（`src/client/wt.rs`）

* 固定 30s Ping 间隔是教科书式 beaconing 信号（被动观测者按周期性即可从 CDN 流量中筛出连接）；
* 落地：每周期重设 `heartbeat_interval()`——30s ± 20%（24..36s 均匀抖动）；
* Pong 判死预算验证：最坏 36s × (PONG_MISS_LIMIT+1) = 108s ≥ 60s，链路半死判定不受抖动影响（测试锁定）。

### F-4 握手帧随机 padding（`src/proto/frame.rs`、`src/client/{wt,fallback}.rs`）

* AUTH 帧（WT + fallback 双路径）与 Open 帧 payload 尾部追加 `[64, 512)` 随机字节，握手密文长度不再是固定协议签名；
* **协议内兼容，服务端零改动**：`decode_open` / `AuthPayload::decode` 按字段前缀解析，尾部自然忽略（回归测试 `open_decode_ignores_padding_tail` 锁定）；
* Data 帧不加：热路径性能敏感，且流式数据长度本身即真实形态。

### F-5 GREASE ECH（新增 `src/client/ech.rs`；`src/client/wt.rs`）

* rustls 0.23.44 内置 ECH 但 `ring` provider 无 HPKE 实现（只有 aws-lc-rs 有，切换 provider 会动整个加密栈且 musl 交叉编译不可行）；
* 新增 HPKE 后端：用纯 Rust `hpke` crate 实现 rustls 的 `crypto::hpke::Hpke` trait——DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + ChaCha20-Poly1305（Chrome 同款 suite），单发 + context 双模式，RFC 9180 往返测试覆盖；
* `build_tls_config()` 改为完全自建 rustls ClientConfig（`with_ech` 必须在 builder 阶段调用），插入 `EchMode::Grease`：ClientHello 携带 `encrypted_client_hello` dummy 扩展，与 Chrome 对无 ECH 服务器的行为一致——anti-ossification + ClientHello 再进一步靠拢浏览器，对不支持 ECH 的服务器零交互；
* 依赖：`hpke = 0.14`（关默认 features，只留 alloc/getrandom/x25519/chacha/hkdfsha2——不拉 ml-kem/x-wing）。

### 明确不做（本轮定性，写入待办）

* **ChromeParrot 等效物**：quinn 把握手外包给 rustls，伪装 ClientHello 需同时 fork quinn-proto + rustls 双层（Hysteria 能做是因 quic-go 自带握手）；
* **Salamander / Gecko 式 UDP 层混淆**：quinn runtime 接管 socket I/O 循环，不支持逐包变换，等效需 fork transport 层。

### 测试与验证

* lib 测试 70 → **78**（+8：心跳抖动 ×2、padding ×2、HPKE ×3、quic_tune ×1）；e2e 11 项全绿——**真实 WT 连接验证零 CID、GREASE ECH ClientHello、padding 帧与现有服务端互通**；
* `cargo fmt --check` 干净、`cargo clippy --all-targets` 零警告。

## 2026-09-13（P2 凭据卫生：配置文件支持，密码搬出 argv 与 docker inspect）

### 配置文件 `--config <path>`（`src/config.rs`、`src/main.rs`）

* `--config` 显式指定（**文件不存在直接报错退出**）；未给时自动探测**当前工作目录的 `newppp.conf`**（不存在则行为完全不变）；
* 格式：`key = value`，**键名 = 命令行长选项名原样**（无独立映射表，键校验直接读 clap 的 `Cli` 定义，永不与 `--help` 漂移）；布尔开关可裸行（`self-signed`）或 `= true`；`#` 注释行；`mode = server|client` → `-s`/`-c`；
* 值引号规则：成对包裹的 `'…'`/`"…"` 剥离、其后内容当注释；未包裹的值原样保留（URL 内 `#`、空格不受影响）；
* 优先级：**命令行 > 配置文件**（实现方式：文件 argv 前置 + `strip_cli_overridden` 去除被 CLI 覆盖的选项 —— clap 4 对重复的 `ArgAction::Set` 会报 ArgumentConflict 而非覆盖，去重在本层做）；文件内部靠后的行覆盖靠前的行；`--auth`（Append 类）双向叠加不互相删除；文件 `mode` 与 CLI `-c/-s` 冲突时以 CLI 认定的模式为准；
* 边角兼容：剥 UTF-8 BOM（Windows 记事本保存的配置文件）；未知 key / 缺值 / 布尔带值 → 报错指明文件与行号，均发生在监听绑定之前（P2-3 校验前移，`--cert/--key` 文件存在性本次一并前移）；
* 凭据卫生：文件含 `auth` 行时检查权限（Unix 下 group/other 有任意权限位 → WARN + `chmod 600` 提示）；
* 测试：新增 6 项（解析/引号/注释/布尔/未知 key/覆盖与 mode 冲突），lib total 63 → 70。

### P0 严重安全：AEAD 跨方向 nonce 重用（`src/proto/crypto.rs`、`src/server/{wt,fallback,hub,state}.rs`）

**问题**

同一会话的客户端与服务端**共享同一把会话密钥**（两端都用 `derive_session_key(static_key, ap.salt)`），而计数器（=ChaCha20-Poly1305 nonce）此前只有「流 / 数据报」两段，**没有按方向分离**：

* WT：客户端首个会话帧计数器为 2（counter 1 被静态密钥的 Auth 帧占用），服务端首个会话帧计数器为 1，二者自 2 起完全重叠；
* 模式 A：客户端会话帧从 1 开始（Auth 用独立编码器/计数器），服务端也从 1 开始，**首帧即同 nonce**。

同密钥同 nonce 加密不同明文 → 密钥流复用（明文异或泄露）+ Poly1305 认证密钥复用（可伪造标签）。属灾难级加密缺陷。

**修复**

把 64 位计数器空间按「通道 × 方向」切成四段互不重叠区间：

| 通道 | 方向 | 区间 |
|---|---|---|
| 流帧 | 客户端 | `[1, 2^62)` |
| 流帧 | 服务端 | `[2^62, 2^63)` |
| 数据报 | 客户端 | `[2^63, 2^63+2^62)` |
| 数据报 | 服务端 | `[2^63+2^62, 2^64)` |

新增 `CounterGen::stream_server()` / `datagram_server()`；服务端全部改用服务端区间（客户端保持不变）。新增回归测试 `counter_spaces_are_direction_disjoint` 断言四段区间两两不交。

**影响与兼容**：接收端不校验计数器的取值范围，因此**先升级服务端**即可对旧客户端也立即消除重用（旧客户端用 `[1,2^63)`，新服务端用 `[2^62,2^64)` 的另一半，天然不交）；仅「新客户端 + 旧服务端」仍为旧的脆弱行为。未改 `PROTO_VERSION`（项目已在 `docs/待办_新.md` 预留 v2 给 Argon2 + 版本协商，故不抢占）。两端都升级后无残留。

**问题**

`udp_associate` 只查 `udp_routes`，不查 `sessions`；而服务端把 TCP 会话也注册进 `sessions`。客户端（已认证）可用与既有 TCP 会话相同的 sid 发 `UdpAssociate`，`register_with` 直接覆盖原会话句柄：旧 token 被孤立、旧配额的释放路径丢失，且 `drop_session` 会连带拆掉该 sid 的 TCP 路由 → 全局 `active_sessions` 泄漏，累积后所有新会话被拒（服务端 DoS）。同一段代码里「先查后插」对 WT 并发专用流也存在 TOCTOU。

### 修复：WT 控制流 `Close`/`Error` 帧泄漏全局会话配额（P1，`src/server/wt.rs`）

**问题**

WT 连接的控制流读取循环里，`Close`（及未处理的 `Error`）帧只调用 `cs2.drop_session(f.sid)`，**没有**调用 `st.release_session()`——对照 mode-A 路径 `hub.rs` 的 `close_tcp`（先 `drop_session` 返回 true 再 release，保证一次性）是漏了释放。后果：每次经控制通路关闭会话都永久扣减全局 `active_sessions` 配额，泄漏累计后服务器因 `>= max_sessions` 拒绝所有新会话（与 `hub.rs` 测试注释里描述的"旧代码重复 Close 下溢配额"同源，但方向相反：假高而非下溢）。

**修复**

`FrameType::Close | FrameType::Error if cs2.drop_session(f.sid) => st2.release_session()`：与 hub.rs 配额语义对齐，guard 保证只有真正移除了注册句柄才释放，重复帧不重复释放。注：当前客户端不在 WT 控制流上发 Close（TCP 会话走专用流的 server 侧 pump 释放），属潜伏缺陷，此为前向兼容加固。

* `Reader::read_bytes` 的越界判断 `self.pos + n <= self.b.len()` 改为 `self.b.len() - self.pos >= n`：消除理论上的 `usize` 相加溢出（debug 断言失败 / release 回绕绕过检查），`pos ≤ len` 为不变式故减法安全。

### 清理：死代码（`src/server/wt.rs`）

删除仅靠末尾 `let _ = sink_ctrl; // keep alive till here` 存活的 `sink_ctrl` 绑定（克隆已存在于各 spawn 任务中，绑定本身无实际作用）；控制流 `_ctrl2` 改为就近从 `ctrl_tx.clone()` 构造。

### 变更：时间源从 SNTP 改为 HTTP `Date` 头（`--time` 接收 URL）

**背景**

SNTP 方案在 Linux 服务端上重试 3 次仍频繁失败（`deadline has elapsed`）：NTP 是单次 UDP/123 交换，受限网络下出站 UDP 常被防火墙/运营商拦截，丢包也无重传保障。TCP 443 出站则几乎不可能被拦。

**方案**

内置时钟的校准源改为任意 HTTP(S) 端点的 **`Date` 响应头**（RFC 7231，秒级精度，对认证 ±60s 窗口绰绰有余）：

* `src/clock.rs` 重写：SNTP 客户端（48 字节 UDP 包、KoD 检测等）全部移除，换为最小 HTTPS 客户端（tokio + tokio-rustls，直接复用依赖树里已有的 rustls，仅新增显式依赖 `tokio-rustls = "0.26"`）；
* 实现：发一个 `HEAD` 请求 → 读 `Date` 头 → RFC 7231 日期解析（自带 Howard Hinnant 民算法，无 chrono 依赖）→ `offset = 服务器时间 − 系统时间`；
* `now = 系统时钟 + offset` 逻辑、每小时同步、每轮 3 次重试（间隔 2s）、失败保留旧 offset 并告警等行为全部保留；
* TLS 强制校验服务器证书（系统根证书）：时钟源被中间人篡改会直接偏移所有认证时间戳，故不做 `--skip-verify` 之类的降级。

**CLI**

```
--time https://www.cloudflare.com/cdn-cgi/trace   # 默认
--time https://time.ms/                            # 任意返回真实 Date 头的站点
--time https://acs.m.taobao.com/gw/mtop.common.getTimestamp/   # 国内推荐
--time http://host:8080/                           # 也支持 http
```

**验证**

* 实测 `time.ms`（offset -1s）、淘宝接口（offset 0s）、默认 cloudflare trace（offset -1s）均正常
* 50 个测试通过，clippy 无警告

**部署**

两端重新构建部署即可。

### 新增：内部 UTC 时钟 + 每小时校准（`--time`，初版为 SNTP）

#### 修复：认证时间戳超出 ±60s 窗口导致连接被拒（时钟偏差问题）

**现象**

服务端和客户端挂了两天后报错，第一天正常：

* 客户端：`WebTransport open failed (wt connect failed: server rejected WebTransport session request); falling back to HTTPS POST`、`server rejected authentication`
* 服务端 DEBUG 日志：收到 CONNECT 请求，bearer 时间戳与服务器当前时间相差 62 秒

**根因**

客户端机器的系统时钟比真实时间快约 62 秒，超出了认证的 ±60 秒时间窗（`AUTH_WINDOW`，`src/proto/crypto.rs`）。Bearer token 与带内 AUTH 帧中的时间戳均按本地时钟生成，服务端校验 `|now − ts| > 60` 时拒绝，表现为会话请求被 404。时钟偏差随时间缓慢漂移（第一天偶发失败、贴着窗口边缘，第二天彻底超窗 100% 被拒），与"挂了两天后报错"的时间线吻合。

**初版实现（SNTP，已被 HTTP Date 方案取代）**

* 新增 `src/clock.rs`：内置最小 SNTP 客户端（RFC 4330），启动即同步、每小时重校，`now = 系统时钟 + offset`（标准 NTP 公式），失败保留旧 offset
* `now_unix()`（`src/proto/crypto.rs`）改走校准时钟，覆盖 Bearer token 与带内 AUTH 帧的时间戳
* 空闲超时用的 `now_millis()`（服务端本地相对时长）不受影响，仍用系统时钟

**期间修复的实现 bug**

1. `interval` 首个立即 tick 被预消耗，导致首次同步要等 1 小时
2. SNTP 请求 T1 时间戳误用 NTP epoch（差 2,208,988,800 秒）导致 offset 计算错误；同时补上 T1（部分服务器拒绝不带 transmit timestamp 的请求）
3. SNTP 单发易丢包：每轮同步加 3 次重试（间隔 2s），单次失败降为 DEBUG 日志
