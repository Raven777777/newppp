# newppp 运维手册

生产部署、Docker 打包、出站安全策略、已知限制与构建质量门。

> 本文档由根目录 [README.md](../README.md) 拆分而来。使用与参数见 [手册.md](手册.md)，协议与安全模型见 [协议文档.md](协议文档.md)。

## Docker 打包（build_docker.py）

把静态 musl Linux 二进制 + Mozilla CA 根证书直接封装成标准 `docker save` 格式（v1.2）镜像 tar——**本机无需安装 Docker**，拷到任意有 Docker 的机器（服务器/NAS）直接 `docker load`。

### 前置：先出 Linux 二进制

```bat
build_linux.bat
```

产物 `target\x86_64-unknown-linux-musl\release\newppp`（静态链接，无需 libc）。

### 打包（交互式启动脚本）

```bash
py -3 build_docker.py
```

依次交互输入**版本号**与**启动参数**（回车打包），例如：

```
请输入版本号: 1.1.0
启动参数: -c --auth alice:secret123 --server https://newppp2.love4z.cn --url wss://newppp.love4z.cn/api/ppp --bind 0.0.0.0:1080
```

启动参数留空则不烧进镜像（运行时在 `docker run` / 容器管理器里填）。打包完成后输出 CA 证书事项与 docker 使用注意（见下方「NAS 容器管理器要点」）。

仍支持原命令行参数（CI 友好）：

```bash
py -3 build_docker.py --version 1.0.0 \
  --args '-c --auth alice:secret123 --server https://newppp2.love4z.cn --bind 0.0.0.0:1080' \
  -o newppp-client-1.0.0.tar --tag newppp-client:1.0.0
```

| 选项 | 说明 |
|---|---|
| `--binary` | 二进制路径，默认 `target\x86_64-unknown-linux-musl\release\newppp`（自动校验 ELF/64 位） |
| `--version` | 版本号（不传则交互输入，作为镜像 tag 与 OCI label） |
| `--args` | 烧进镜像 Cmd 的启动参数，必须以 `-c` 或 `-s` 开头；`-c` 时 ExposedPorts 自动变为 1080/tcp（不传则交互输入） |
| `--tag` / `-o` | 镜像标签与输出文件名，默认 `newppp:<版本号>` / `newppp-<版本号>.tar` |

打包时自动从 curl.se 下载 Mozilla CA bundle 并注入镜像（本地缓存 `.cacert.pem`，删除即强制重新下载）。

### 导入与运行

```bash
docker load -i newppp-client-1.0.0.tar

# 服务端容器（自签调试；正式部署挂载证书改用 --cert/--key）
docker run -d -p 80:80 -p 443:443/tcp -p 443:443/udp newppp:1.0.0 -s \
  --auth alice:secret123 --listen 0.0.0.0:443 \
  --fallback-listen 0.0.0.0:443 --http-listen 0.0.0.0:80 --self-signed

# 客户端容器
docker run -d -p 1080:1080 newppp-client:1.0.0
```

### NAS 容器管理器要点

* 镜像已自动注入 Mozilla CA 根证书（`/etc/ssl/certs/ca-certificates.crt`，`build_docker.py` 打包时从 curl.se 下载），scratch 基座的 `UnknownIssuer` 问题已解决，无需 `--skip-verify`；根证书随镜像打包，长期不更新可能过期，重新打包即刷新。
* 镜像 Cmd 已含完整启动参数时，**「容器运行命令」留空保持默认**，不要填——多数管理器会把整行命令当成单个参数导致 `container startup failed`。
* 端口映射只加 `本地端口 → 1080/TCP`（客户端）；443/udp、80 是服务端端口，客户端容器不需要。
* 容器内必须绑 `0.0.0.0`（如 `--bind 0.0.0.0:1080`），写 127.0.0.1 会导致映射失效。
* `--args` 里的密码会写进镜像配置（`docker inspect` 可见），镜像 tar 请妥善保管。

## 生产部署

### 档位 3：后端直出（无 nginx，单进程）

即 [手册.md](手册.md#快速开始) 的服务端命令，`--cert/--key` 换成真实证书（Let's Encrypt，`--acme-dir` 支持 http-01 续期）。伪装站与代理逻辑耦合在一个进程里，改伪装页要动后端。

### systemd 常驻（deploy/newppp.service）

档位 1 / 档位 3 的服务端都建议用 systemd 常驻。项目自带单元文件 `deploy/newppp.service`（含 `Restart=on-failure` 自动拉起与 `NoNewPrivileges`/`ProtectSystem=strict`/`ProtectHome`/`PrivateTmp` 加固）。

1. **放置二进制与证书**：

   ```bash
   sudo install -m 755 newppp /usr/local/bin/newppp
   sudo useradd -r -s /usr/sbin/nologin newppp     # 专用系统用户
   sudo mkdir -p /etc/newppp
   sudo cp cert.pem key.pem /etc/newppp/
   sudo chown -R newppp:newppp /etc/newppp
   sudo chmod 600 /etc/newppp/key.pem
   ```

2. **改 `ExecStart`**（单元文件内备好两种档位，改用户密码即可）：
   * 档位 1（nginx 前置，默认段）：后端只听回环 `--listen 127.0.0.1:8443 --fallback-listen 127.0.0.1:8444`；
   * 档位 3（后端直出，注释段）：`--listen 0.0.0.0:443 --fallback-listen 0.0.0.0:443`，防火墙放行 UDP/TCP 443、TCP 80。

3. **安装并启用**：

   ```bash
   sudo cp deploy/newppp.service /etc/systemd/system/newppp.service
   sudo systemctl daemon-reload
   sudo systemctl enable --now newppp
   ```

4. **验证**：

   ```bash
   systemctl status newppp
   journalctl -u newppp -f          # 应出现 "newppp server started (...)"
   ss -ulnp | grep 8443             # 档位1确认 UDP 监听
   newppp healthcheck --url http://127.0.0.1:9100/healthz   # healthy: 退出码 0
   ```

### 优雅停机与 systemd 配套（P3-1/P3-5）

收到 SIGTERM/SIGINT 后服务端按固定序列收尾：cancel 全部活跃连接（QUIC 发 CONNECTION_CLOSE，会话泵级联取消）→ 排空在途会话（`--shutdown-grace`，默认 10s；超时强杀并 WARN）→ drop 监听句柄 → **退出码 0**。该时序已被 e2e `graceful_shutdown_releases_ports` 验证：WT（UDP）与 fallback（TCP）端口在进程退出后立即可复用，不会再出现 QUIC endpoint driver 拖延释放的残留。

对应到 systemd 单元（`deploy/newppp.service`）：

* `KillSignal=SIGTERM` — 停止信号交给进程自身走优雅路径；
* `TimeoutStopSec=15` — 须大于 `--shutdown-grace`（默认 10s），给 systemd 强杀（SIGKILL）前留余量；
* `Restart=on-failure` — 优雅停机退出码为 0，不触发重启；崩溃（非 0）才自动拉起。

验收：`systemctl stop newppp` 后 `journalctl -u newppp` 无 panic，且随后 `systemctl restart` 配置无误时能看到新的启动成功日志。

### 健康检查（--health 与 healthcheck 子命令）

P3-2/P3-3：NAS 容器管理器和 systemd 之外判断"进程活着但链路死了"的唯一手段。

* 服务端/客户端共用 `--health 127.0.0.1:9100`：进程内挂起一个**仅回环推荐的**明文 HTTP 监听，`GET /healthz` 返回 JSON：

  ```json
  {"uptime":3,"active_sessions":0,"wt_conns":0,"transport":"mixed","circuit":"closed","last_fallback_at":null}
  ```

  * `active_sessions` / `wt_conns`：当前的会话总数与活跃（已认证）连接数；服务端 0 未必是故障（空闲本来就是 0），要结合 `uptime` 与日志看。
  * `transport`：`wt`（仅 WT 监听）/ `fallback`（仅 HTTP 兜底）/ `mixed`（双监听）；客户端侧表示出站配置形态。
  * `circuit`：客户端 WT 主路径熔断状态（`closed` 正常 / `open` 正走兜底冷却中）。
  * `last_fallback_at`：客户端最近一次兜底接管的时间（Unix 毫秒，从未用过为 null）——常开非 null 说明主路径长期不健康。

* `newppp healthcheck --url http://127.0.0.1:9100/healthz`：一次性探测子命令，200 且响应含 `uptime` 字段才判健康，退出码 0（健康）/1（不健康）。scratch 镜像无 shell，docker `HEALTHCHECK` 必须由二进制自身实现——`build_docker.py` 打包时自动写入该指令（探测容器内 `127.0.0.1:9100`，无需额外端口映射），并给烧入的启动参数自动补 `--health 127.0.0.1:9100`（可显式指定，探测地址随之更新）。

> 注意：`ProtectSystem=strict` 下整个文件系统只读，`/etc/newppp` 证书保持可读即可，不要把运行时需写的目录放进单元；`--self-signed` 开发模式写 `/tmp`，`PrivateTmp` 已覆盖。

### 简易常驻：screen

不想配 systemd 时，用 `screen` 把服务端挂后台（需先 `apt install screen` 或 `yum install screen`）。注意这只是简易方案：**开机不自启、崩溃不拉起**，长期运行请用上面的 systemd。

1. **创建会话并启动**：`session_name` 自取，回车后进入会话窗口，正常输入启动命令：

   ```bash
   screen -S newppp
   newppp -s --auth alice:secret123 --listen 0.0.0.0:443 \
     --fallback-listen 0.0.0.0:443 --http-listen 0.0.0.0:80 \
     --cert /etc/newppp/cert.pem --key /etc/newppp/key.pem
   ```

2. **分离会话**：按 `Ctrl+a` 再按 `d`——暂时退出窗口，进程继续在后台跑，可安全断开 SSH。

3. **重新连接**：

   ```bash
   screen -r newppp     # 回到会话（即可看到服务端日志）
   screen -ls           # 列出所有会话
   ```

4. **关闭会话/停止服务**：`screen -r newppp` 回到会话后，`Ctrl+C` 停掉服务端，再输入 `exit` 关闭会话；或一步到位（不进会话直接杀掉）：

   ```bash
   screen -S newppp -X quit
   ```

客户端同理：把启动命令换成 `-c ...` 参数即可。

### 档位 1：nginx 前置

nginx 无法反代 WebTransport/h3 会话，职责划分（`deploy/nginx.conf`）：

1. **UDP 443**：nginx `stream` 模块透传给后端 `--listen`（后端用同一张证书终止 QUIC-TLS）。
2. **TCP 443**：nginx 终止 TLS，`/api/ppp` 反代后端 `--fallback-listen`（降级），其余路径服务伪装静态站。
3. 服务端 systemd 直跑（`deploy/newppp.service`），双监听 `127.0.0.1:8443` / `127.0.0.1:8444`。
4. 证书：certbot（Let's Encrypt），证书同时给 nginx（TCP）与后端（QUIC）。
5. 防火墙仅放行 UDP 443 / TCP 443 / TCP 80。

所有流式路径必须 `proxy_request_buffering off; proxy_buffering off;`（见 nginx.conf），否则交互流量会被缓冲；本实现已发送 `X-Accel-Buffering: no`。

### 档位 2：Cloudflare 前置

CF 的代理模型是"**边缘终止一切，仅 TCP 回源**"——QUIC/UDP 在标准橙云代理下到不了源站。各路径可行性（均零代码改动）：

| 路径 | 可行性 | 原因 |
|---|---|---|
| WT 主路径穿 CF | ❌ | CF 边缘终止 QUIC，不转发 WT 会话（会话流被重置；客户端会自动回落） |
| WS/POST 通道用 QUIC | ❌ | 回源仅 TCP；客户端 wss 走 h1.1 升级，本就不经 QUIC |
| HTTP/3 回源 | ❌ | CF 即便 h3 回源也只发普通 h3 请求，源站 UDP 443 只应答 WT 会话 |
| Workers 桥接 | ❌ | Workers `connect()` 仅 TCP，无 UDP socket |
| cloudflared Tunnel | ❌ | cloudflared↔边缘之间是 QUIC，但客户端侧仍是 HTTP |
| **Spectrum** | ⚠️ 唯一例外 | L4 代理可转发 UDP：UDP 443 直通源站则 WT 全链路可用（付费，Enterprise/加购） |

**橙云下唯一可行承载是 WebSocket 降级通道（形态 B-CF）**：

1. DNS 橙云代理 `newppp.love4z.cn`（免费版即可，无需开启任何 WS 开关——CF 默认支持）；
2. SSL/TLS 模式建议 Full（strict）；
3. 客户端 `--url wss://newppp.love4z.cn/api/ppp`，其余不变；
4. 注意 WS 单条消息上限与空闲超时由 CF 管理：本实现帧 ≤~17KB、30s 心跳，均在安全范围内；
5. 服务端日志中 WS 通道与 POST 通道均表现为 mode-A 连接（认证/限速/回收逻辑一致）。

**推荐组合拳（免费、兼顾隐藏与性能）**：主域名橙云走 wss 保底，另开一个**灰云子域**（如 `wt.love4z.cn`，仅 DNS，A 记录指向源站）专跑 WT 主路径；客户端两个都配——WT 走灰云子域，传输层故障自动回落到橙云 wss 通道（不要求隐藏源站 IP 时，把兜底换成灰云直连 POST 更快，见 [手册.md](手册.md#域名路由速查走不走-cf-看云朵不看-scheme)）：

```bash
newppp -c --auth alice:secret123 \
  --server https://wt.love4z.cn \
  --url wss://newppp.love4z.cn/api/ppp \
  --bind 127.0.0.1:1080 --http-bind 127.0.0.1:8081
```

若完全不需要隐藏源站 IP，全灰云直连（`https://` POST 通道 + WT 主路径）延迟最低。

## 服务端出站安全策略

默认策略只允许公网目标。服务端会在 TCP/UDP 连接前解析并过滤目标地址，拒绝 loopback、私网、链路本地、未指定、多播、CGNAT、保留/文档网段，以及 IPv4-mapped IPv6 对应的非公网地址。

如确实需要访问本机或内网目标，显式添加：

```bash
newppp -s ... --allow-private-targets
```

该选项会放宽服务端出站限制，应仅用于可信用户和受控网络。

## 日志词汇表（P4-2）

> 日志级别过滤用 `--log`，临时调住可设 `debug`；下面凡标 DEBUG 的默认不可见。词汇按"启动 → 稳态运行 → 收尾"排列；每条都给出**成对关系**（对端/镜像日志是哪条），这是判断"谁先出的问题"的唯一线索。

### 启动序列（两端一致，正常启动应依次完整出现）

| 日志 | 含义 | 缺失说明 |
|---|---|---|
| `user '<uid>' registered`（服务端） | `--auth`/配置文件每个用户一条 | 没有这条说明参数解析失败——启动本身已报错退出 |
| `WebTransport (QUIC/h3) listening on udp://<addr>` | WT 监听就位 | bind 失败会以 Error 直接退 |
| `HTTPS fallback (mode A POST + disguise) listening on tcp://<addr>` | TLS 降级/伪装站就位 | 同上 |
| `HTTP front (301 → HTTPS, ACME http-01) listening on tcp://<addr>` | 80 门面就位（配了 `--http-listen` 才有） | — |
| `newppp server started (max_sessions=…, shutdown_grace=…)`（服务端）| **启动成功**的标志（journalctl 里确认是否正常起来就看它） | 只有它到、监听缺 → 对应监听配置了但端口没绑上 |
| `newppp client up (outbound: …)`（客户端） | 出站构建完成 | — |
| `SOCKS5 listening on <bind>` / `HTTP proxy listening on <bind>`（客户端） | 本地入站就位 | — |
| `<label> health endpoint on http://<a>/healthz` | `--health` 配置时才有 | — |
| `clock synced with <time> (offset ±Ns)`（两端） | **每次重要校准都会打印**：与 `--time` URL 对表成功 | 认证类报错（见 checklist）先看它时间戳新旧 |
| `WebTransport (QUIC/UDP) listener disabled (--listen not set): pure-website mode` | 配置选了不打 WT 口（纯网站形态） | — |
| WARN `using self-signed dev certificate (…)` | `--self-signed` 调试模式 | 生产必须换成真实证书 |
| WARN `config file <path> is readable by group/other while it contains passwords — run: chmod 600 …` | 配置文件权限过宽（P2-1） | 若已 chmod 还见，可能是容器/挂载层的 umask |
| WARN `--listen <addr>: IP part is ignored — WebTransport always binds all interfaces` | `--listen` 存在 IP 部分（已知限制，IP 部分被 wtransport 绑定 API 忽略） | — |

### 稳态运行（偶发，关键是判断"成对出现 vs 孤儿出现"）

| 日志 | 含义 | 成对 / 处置 |
|---|---|---|
| 服务端 `wt conn authenticated uid=<uid>` | 该用户一条 WT 连接认证成功 | **反复出现 = 重拨自愈**：成对看客户端 `wt connection dead` / 连接池 `pool maintenance …`；客户端稳定时反复出现也是正常补活 |
| 客户端 `wt connection established -> <url>` | 同上（客户端视角） | 与上一条总是同键 |
| 客户端 WARN `wt connection dead: <reason>` | 一条 WT 连接终结（原因带 QUIC 关闭原因/心跳 Pong 超时/控制流关闭）；**死因含 `too many gaps` 时自动追加 `--recv-window` 调参提示** | 和服务端 `wt auth: protocol version mismatch`（版本错乱时）或 `wt conn ended` 结束日志对照排查 |
| DEBUG `reaping idle conn <id> (uid=…)`（服务端） | 空闲回收器按 `--idle` **按期回收**空连接/死会话 | **设计行为**，勿当错误；持续出现说明客户端更低发（空闲连接留存调试时把 `--idle` 调大） |
| 服务端 WARN `fallback: missing/bad in-band auth` | 模式 A（POST/WS）遇到一个未通过认证的通道 | 偶发 = 扫描者；**频繁 = 密码偏差/时钟偏差**，先查 checklist 时钟项 |
| 服务端 WARN `replayed bearer token` / `replayed auth nonce`（uid=…） | 防重放缓存命中 | 同一 token 第二次请求（可能是重放攻击）；也可能是客户端重连过快复制了同一 token |
| 客户端 DEBUG `fallback channel died; reconnecting: …`（两端） | 兜底通道掉线重拨（池/重试自动） | 降级链日常翻转时整个这个区段都是 DEBUG 式的，无需惊动 |
| WARN `WebTransport open failed (…) ; falling back to HTTPS POST`（客户端） | 主路径一次会话建连失败，自动走兜底成功 | 单发无所谓；连发 + 下条 = 熔断 |
| WARN `WebTransport unstable: primary path cooling down for 60s`（客户端） | **熔断器已打开**：3 次传输层故障 | 见 checklist 第 3 项；冷却到期后放行探测，成功自动 close |
| DEBUG `WT circuit open: <dst> goes to fallback directly` | 熔断中，主路径跳过 | 同上 |
| DEBUG `mux client/server: bad frame` / `server mux: bad UdpData payload` / WARN `mux encode failed` | 编解码护栏，坏帧被丢弃而不是让连接崩 | 偶发=链路贴坏帧；频繁=链路质量差或版本混杂 |
| DEBUG `refusing connection from <remote>: unauthenticated cap reached`（服务端） | `--max-unauth` 上限拒入 | 认证洪水；黑名单/防火墙 |
| DEBUG `incoming connection failed:` / `session accept failed:` | 握手层错误（扫描者常见） | 看上下文 IP 是否来源可靠 |

### 停机与收尾

| 日志 | 含义 | 成对 |
|---|---|---|
| `shutdown signal received`（两端） | SIGTERM/SIGINT（Windows 上是 Ctrl+C/服务停止） | — |
| 服务端 WARN `a listener exited; shutting down` | **孤儿**监听任务退出（bind 失败/被抢占），作为失败收尾的信号 | 正常收尾不改它（正常停机由 `shutdown signal received` 说明） |
| `graceful shutdown: closing N live connection(s), draining up to 10s` | 优雅停机运行中 | — |
| `graceful shutdown: drain complete` / WARN `drain timeout … force-closed` | 排空完成 / 超时强杀 | 超时说明会话卡在慢网，把 `--shutdown-grace` 调大一点 |
| 客户端 `shutdown signal received` → 入站/出站端口释放 | 客户端收尾 | — |

## 排障 checklist（P4-3）

1. **起不来（连不上、启动即退）**：找 journalctl/stdout 的最后一条 Error。可能原因与其来源：
   * `cert file not found` / `key file not found` — P2-3 校验前移（路径打错在 bind 前就退）；
   * `config file not found`（显式 `--config`）、`newppp.conf:<行>: unknown option/needs a value`（语法）— 配置文件；
   * `bind … AddrInUse`（Error）— 端口被占，改端口或停掉旧进程；
   * `server needs --auth/--cert/--key/--listen` — 参数必填项缺。
2. **链路死/总是"慢"**：客户端进程活着但 `curl` 卡：
   * 客户端日志搜 `wt connection dead` 统计死因；死因带 `too many gaps` → **调 `--recv-window 1..2`**（高丢包），反之高 RTT 低丢包可调大提速；
   * 间歇性 `cooling down`（熔断反复触发）→ 主路径（UDP）长期不稳，检查防火墙/运营商 UDP 情况；兜底一直顶上 → 这是降级链在工作，不是"代理坏了"。
3. **认证类被拒**（连接建、AUTH 不过）：
   * **先查时钟**：两端 `clock synced` 时间戳是否新（>1h 未见 → 时间源不可达，端点时间差 >±120s 会拒 AUTH）；
   * 然后查 `replayed bearer/nonce` — 同一 token 多发（可能重放攻击或客户端 bug）；
   * 再查密码 & uid 拼写（`auth = 2233:…`，uid 限 `[A-Za-z0-9_-]{1,32}`）。
4. **TLS 握手被拒（`--pin` 用户）**：客户端日志报 `certificate fingerprint mismatch (--pin)` → **服务器证书换过了**（LE 续期/重签），指纹与客户端配置不再一致。处置：服务器重算指纹（`openssl x509 -in cert.pem -noout -fingerprint -sha256`）→ 更新客户端配置 `pin = ...` → 重启客户端（详见 [手册.md](手册.md#pin-指纹获取与轮换)）。档位 1（nginx 终止 TLS）下 pin 的是 nginx 的证书——nginx 换证书同样触发。
5. **fallback 一直顶**：`X-Newppp-Error` 出现的 dial-failed（目标侧）和 transport failure 不同；`caught too many gaps` 与降级冲突见第 2 条；服务端在 nginx 档位 1 下要看到 `HTTPS fallback … listening on 127.0.0.1:8444` 后 nginx `proxy_buffering off` 生效。
6. **Docker/NAS**：CONTAINER unhealthy → 容器内 `--health` 参数确实自动注入（`docker inspect` 看 Cmd 含 `--health`）；**进程被反复拉起**（Restart=always/on-failure）→ 看最后日志是否有 panic 级 Error（正常退出码 0 不会被误重启）；**优雅停机**——`docker stop` 应在 `--shutdown-grace+余量` 内收尾并退出码 0（见运维手册「优雅停机」节）。
7. **一行 grep 快速定位**（systemd：`journalctl -u newppp -f`）：

   ```bash
   journalctl -u newppp --since "1 hour ago" | grep -E "too many gaps|wt connection dead|cooling down|reaping idle|a listener exited|unauthenticated|missing/bad in-band|replayed|fingerprint mismatch" | tail -50
   ```

   （客户端容器是 `docker logs <id> 2>&1 | grep -E "wt connection dead|cooling down|too many gaps"`。）

## 已知限制 / 风险

* **套 Cloudflare 时不要配 `--server`（WT 主路径）**：CF 边缘接受 h3 但不支持 WebTransport，会重置 WT 会话流——旧版 wtransport(0.6) 会因此 panic（0.7.2 已修复，重置被正常归类为连接错误并自动回落）；CF 后请用 `--url wss://`（见档位 2）。
* `--listen` 提供时仅端口生效（wtransport 绑定 API 限制），总是绑定全部接口；启动时会输出 WARN 提示 IP 部分被忽略。需要限定地址时用防火墙/iptables 收敛，或省略 `--listen` 完全不监听 UDP。
* **未认证连接**：服务端默认对未认证连接设上限（全局 `--max-unauth`，默认 128；每源 IP 为其 1/8，2..64）。连接在通过 AUTH 帧前占用名额，认证成功后立即释放，因此不影响已认证会话的正常并发；超限连接被静默丢弃。
* quinn 的 QUIC/TLS 指纹已部分对齐浏览器（2026-09-14 F 系列：单连接时零长度源 CID、多连接时 8 字节源 CID、8 字节初始 DCID、TP 数值、GREASE ECH、心跳去周期化、握手帧 padding，见 [协议文档.md](协议文档.md#浏览器指纹对齐与隐蔽性f-系列2026-09-14)）；残留：quinn 硬编码总是发送的 `min_ack_delay` / `grease_transport_parameter` / `write_order` 三个 TP，深度分析仍可判定"非 Chrome"，消除需 fork quinn-proto（明确不做）。被动分类特征已减少，但不能宣称无特征。
* **`--pin` 证书轮换即失效**：pin 锚定的是握手对端的那张证书——换证书（Let's Encrypt 续期、重新自签）后指纹变化，客户端全部拒绝连接（日志报 `certificate fingerprint mismatch (--pin)`）。`--pin` 的预期组合是自签/长有效期证书；LE 自动续期部署不要用 `--pin`（也不要用 `--sni`，伪装与 LE 证书互斥）。轮换操作顺序与获取方法见 [手册.md](手册.md#pin-指纹获取与轮换)。
* `too many gaps in stream buffer`：quinn 对流重组缓冲乱序空洞数的内部保护，丢包/乱序严重的弱网 UDP 链路 + 大接收窗口下会触发，触发后该连接中止、会话自动回落 HTTPS POST。接收窗口默认 2MB（300ms RTT 单流 ≈ 53Mbps），可用 `--recv-window` 调节（1..=64 MB）：高丢包调小（如 1）、优质高延迟线路调大提速。**触发时客户端 `wt connection dead` 与两端连接结束日志会自动附上调参提示**（`--recv-window 1..2`），grep `too many gaps` 即可定位。
* **WT 主路径熔断**：连续 3 次传输层故障（连接被杀、握手失败等）后熔断 60s，期间新会话直接走兜底不再试错；到期放行一次探测，成功恢复、失败立即再熔断。目标侧拒绝（拨号失败/限额）不计入——那是传输健康、目标不可达。
* UDP 443 不应答普通 h3 GET（也不发 Alt-Svc）：浏览器不会来（无 Alt-Svc），但定制探测工具可发现"这个 QUIC 服务不是网页"；WT 握手探测则得到 404，与"不支持 WT 的普通源"一致。根治需换 quinn+h3 栈实现 GET/WT 同端口共宿——留作后续演进（[待办_新.md](待办_新.md) 「暂不做」）。
* 流量形态：长连接多流持续传输（像视频会议/云盘），内容级分析对任何形态都有告警可能。
* 降级路径（模式 A）依赖 nginx 关闭缓冲；本实现已发送 `X-Accel-Buffering: no`。
* UDP 数据报 >路径 MTU 时自动改走可靠流（PMTUD 上限 ~1200B 设计）；形态 B 下 UDP 全走可靠流。

## 构建与质量门

```bash
cargo build --release                              # 产物 target/release/newppp
cargo fmt --all -- --check                         # 格式检查
cargo clippy --all-targets -- -D warnings          # 静态检查（0 警告基线）
cargo test                                         # 单元/property 测试（93 项，含回归）+ 进程内 e2e（14 项）
cargo test --test e2e                              # 仅跑端到端：tests/e2e.rs（单进程起真实 server+client）
cargo bench --bench frame                          # 帧热路径 criterion 基准
py -3 tests/e2e_local.py                           # 本地端到端（多进程：可执行文件 + 回环，11 项检查）
```

当前质量门结果：`cargo test --all-features` 93 项 lib 测试 + `tests/e2e.rs` 14 项 e2e 全部通过（含 SNI 伪装 + pin 回归、限速语义回归和连接池源 CID 回归）。e2e 在**单进程内**用真实的服务端监听器（WT + TLS）与真实的客户端栈（`Outbound` + SOCKS5/HTTP 入站）驱动，覆盖：HTTPS POST / WebSocket 降级、SOCKS5 CONNECT 与 UDP ASSOCIATE（回环 echo）、>MTU UDP 数据报自动落流、认证矩阵（坏 bearer→伪装页 / 坏 AUTH 帧 / 错钥 AUTH 帧 / nonce 重放）、私网拒绝与 `--allow-private-targets` 放行、TCP 半关闭（WT + 模式 A 双路径）、降级链与熔断（3 次故障→熔断→冷却半开）、目标侧失败不触发降级、生命周期收尾（配额归零 + 监听端口立即可复用）、优雅停机（cancel → 排空 → drop 监听，WT/fallback 端口立即 rebind）。F 系列指纹改动（源 CID / GREASE ECH / padding / 心跳抖动）均由该 e2e 网验证与现有服务端互通（服务端零改动）。`tests/e2e_local.py` 保留作多进程形态的旁路验证。

CI：单文件 [.github/workflows/ci.yml](../.github/workflows/ci.yml)——push/PR 跑 `fmt --check`、`clippy --all-features --all-targets -D warnings`、`cargo test --all-features`；每周定时 `cargo-audit`；打 tag 产出 musl 静态二进制 artifact。**bench 不进 CI**（criterion 噪音大，留本地）。

## 发布流程（P4-4，手动分发）

不做自动发布：tag 只触发 CI **构建并上传 artifact**，由管理员手动取件、打包、分发。

1. **打 tag**：

   ```bash
   git tag v0.2.0 && git push origin v0.2.0
   ```

   CI 触发两个工作：`check`（fmt/clippy/test 全量）+ `musl`（Ubuntu 出 `x86_64-unknown-linux-musl` 静态二进制）。

2. **取件**（GitHub Actions 页 → 对应 tag run → Artifacts `newppp-linux-x86_64-musl`），或本地自行出件：

   * Linux 静态二进制：`build_linux.bat`（zig-lld 交叉编译，产物 `target\x86_64-unknown-linux-musl\release\newppp`）；
   * Windows 本机：`build_release.bat`（产物 `target\release\newppp.exe`）。

3. **打 Docker 镜像 tar**（本机无需 Docker）：

   ```bash
   py -3 build_docker.py --version 0.2.0 --args '-s --config /etc/newppp/newppp.conf'
   ```

   产物 `newppp-0.2.0.tar`（标准 `docker save` 格式，CA bundle 自动注入；启动参数建议只烧 `--config`，真实凭据挂载卷内配置文件，见上文 Docker 打包节）。交互式版本号/启动参数亦可直接 `py -3 build_docker.py`。

4. **手动分发**：镜像 tar / 静态二进制自行保管分发（网盘、scp 均可），**不使用 GitHub Releases 自动发布**——包内含凭据健康审计（镜像 tar 由管理员自己核对 Cmd）。

5. **验证**：`newppp --version` 输出与 tag 一致；冷启动应看到上面「启动序列」的完整日志链。

代码基线：无 `unsafe`、无 `#[allow]` 压制；应用显式配置的 TLS/加密 provider 使用 `ring`，但依赖树仍可能因上游 Rustls 生态包含传递依赖 `aws-lc-rs`，不能据此保证构建完全不触发相关构建依赖；GREASE ECH 的 HPKE 后端为纯 Rust `hpke` crate（关闭默认 features，不拉 ml-kem/x-wing）；edition 2021，MSRV 为 Rust 1.88，当前验证工具链为 Rust 1.97。未安装 `cargo machete`，因此未将“无未用依赖”作为已验证结论。
