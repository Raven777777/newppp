# newppp 协议文档

架构、帧协议、加密与认证、内部时钟、会话生命周期、隐私与安全模型与性能基线。

> 本文档由根目录 [README.md](../README.md) 拆分而来，用于冻结当前实现，作为将来改协议时的对照基线。使用与参数见 [手册.md](手册.md)，生产运维见 [运维手册.md](运维手册.md)。

## 架构

| 路径 | 说明 |
|---|---|
| **WebTransport (h3/QUIC)** | 主路径。TCP 会话 = 1 条 bidi 流；UDP = QUIC DATAGRAM（超 MTU 自动落流降级）；控制帧走首条控制流 |
| **HTTPS POST（模式 A 降级）** | 单个双工 POST，请求/响应 Body 承载全部帧协议（TCP+UDP），SessionID 多路复用（DashMap + 有界 mpsc，容量 256） |
| **WebSocket（模式 A 变体）** | 同一套帧协议与认证，承载在一条 WebSocket 双工通道上（`wss://`）；专供 Cloudflare 等会缓冲请求体的代理环境使用 |

降级链：`WebTransport → HTTPS POST`，**按错误类型**切换：

* **传输层故障**（连接断、握手超时、`too many gaps` 等协议层异常）→ 杀掉该连接并回落 HTTPS POST，会话在降级通道上重建；
* **目标侧拒绝**（服务端拨号失败 `DialFailed`、目标非法、限额）→ 按会话直接返回错误：降级通道拨的是同一个目标、走同一个服务端，回退只会重复同样的失败，还会白白摧毁一条承载着其他会话的健康 QUIC 连接（仅限额类错误会尝试回退，因为降级通道有独立容量）；
* **熔断器**：连续 3 次传输层故障后主路径熔断 60s，期间新会话直接走兜底、零试错；到期放行一次探测，成功恢复、失败立即再熔断。目标侧拒绝不计入——那说明传输本身是健康的。

fallback 服务端对拨号、DNS 和 UDP 工作使用每连接最多 32 个并发 worker；达到上限后施加背压，避免单条连接上的慢目标耗尽任务资源或阻塞其他会话。

## 帧协议（20 字节定长头，小端）

```
0     1     2     4     8     12         20
+-----+-----+-----+-----+-----+----------+
| ver | type|flags| sid |ctlen| counter  | + ciphertext||tag
+-----+-----+-----+-----+-----+----------+
```

* `type`：Auth / AuthOk / Open / OpenOk / OpenErr / Data / Close / Ping / Pong / UdpAssociate / UdpOk / UdpData / Error
* `flags`：FIN（半关闭）、RST（中止）
* AAD = 头部前 12 字节；计数器即 AEAD nonce。计数器空间按**通道 × 方向**切成四段互不重叠区间（客户端/服务端共享会话密钥，方向必须分离，否则同 nonce 重用是灾难性的）：客户端流 `[1, 2^62)`、服务端流 `[2^62, 2^63)`、客户端数据报 `[2^63, 2^63+2^62)`、服务端数据报 `[2^63+2^62, 2^64)`
* 数据报接收端带 64 位滑动窗口抗重放
* **帧负载上限协商（v2）**：`ctlen` 为 u32，但明文帧长上限在握手时协商——`AuthPayload` 尾部携带本端可接收的最大明文帧长（`max_plaintext`，字节），服务端取双方较小值（下限 16 KiB = v1 基线，上限 1 MiB）并在 `AuthOk` 回显（WT 与模式 A 双路径都回显）；客户端据此设置编码器后才发送数据帧。`--max-frame-kb`（16..=1024，默认 16）是唯一调节项，两端都调大才会生效（取小值）。下限保持 16 KiB 使既有 16 KiB 读缓冲全部合法，只有 UDP 负载能从更大值受益。

## 加密与认证

* 外层：QUIC-TLS（合法证书，标准握手）——QUIC 强制 TLS 1.3，流量全加密
* 内层 E2E：`static_key = HKDF-SHA256(password, salt="newppp-v1", info="newppp/auth/<uid>")`；会话密钥 = HKDF(static_key, 客户端随机 salt)；ChaCha20-Poly1305
* 双重认证：`Authorization: Bearer <uid>.<ts>.<nonce>.<HMAC>`（±60s 时间窗，饱和比较防溢出 + nonce 防重放缓存：同一 token 只接受一次；容量 5 万，按时间戳过期自动清理，不会整表清空）+ 首帧 AUTH（静态密钥封装，携带 salt 换会话密钥，nonce 同样防重放）
* **协议版本显式协商**：AUTH 载荷首字节为 `proto_version`（当前 **2**）。服务端在解出载荷、确认 uid 后先比对版本；不匹配时内部识别为 `VersionMismatch`，输出 `protocol version mismatch (client=X, server=Y)` 的 ERROR 日志，然后按认证失败路径结束连接/返回伪装响应，而不是向未信任对端暴露详细错误。版本检查先于 nonce 记录，版本不合不消耗重放名额。帧头 `ver` 字节仍负责头部布局校验，两者互补。v2 相对 v1 的全部差异是 AUTH 载荷尾部追加 `max_plaintext`（帧上限，见「帧协议」）并在 `AuthOk` 回显；v1 载荷无此字段，解码时按 16 KiB 基线补齐，从而仍以版本不匹配报出而非解码失败。两端需同步升级。
* **认证失败不返回 401**：WT 会话请求返回 404；HTTP 降级端点返回伪装页（200）
* 只用标准 Header，UA 伪装 Chrome
* 隐私边界与威胁模型取舍见下方「隐私与安全模型」章节

## 内部时钟（HTTP Date 校准）

认证时间戳有 ±60s 窗口，要求两端时钟大致一致。现实部署中客户端机器时钟漂移几十秒并不罕见（**快 60s 以上时认证全部被拒**，表现为 `server rejected WebTransport session request` / `server rejected authentication`）。为此进程不直接信任系统时钟：

* 内部维护 UTC 时钟 `now = 系统时钟 + offset`，offset 由 HTTPS 响应的 **`Date` 头**（RFC 7231，秒级精度，对 ±60s 窗口绰绰有余）校准得出；
* **启动时立即同步一次，之后每 1 小时重新校准**；每轮最多 3 次尝试（间隔 2s）；
* 选 HTTP 而非 NTP 是刻意的：TCP 443 出站几乎不可能被防火墙拦，而 NTP 单次 UDP/123 交换在受限网络/高丢包链路下经常丢失；
* `--time` 可指定任意 `https://`（或 `http://`）URL（默认 `https://www.cloudflare.com/cdn-cgi/trace`）——任何返回真实 `Date` 头的站点都能当时间源，比如 `https://time.ms/`、`https://acs.m.taobao.com/gw/mtop.common.getTimestamp/`；
* 首次同步成功前退化为系统时钟；同步失败不阻塞启动、保留旧 offset 并告警；
* **日志静默 = 同步成功**：offset 与上次不同时输出 INFO `clock synced with <url> (offset Ns)`；offset 恰好为 0s 或某轮之后不再变化（prev == off）时降级为 DEBUG 静默——**没看到日志不代表没同步**。想观察每轮结果用 `--log debug`；3 次尝试全失败仍输出 WARN 并保留旧 offset；
* 客户端与服务端都校准：即使两端各差几十秒，校准后都贴近真实 UTC，±60s 窗口自然满足。

```bash
newppp -c ... --time https://time.ms/                                      # 客户端（默认 cloudflare）
newppp -s ... --time https://acs.m.taobao.com/gw/mtop.common.getTimestamp/  # 服务端（国内推荐淘宝接口）
```

## 会话生命周期与稳健性

* **全局会话配额恰好一次释放**：配额释放与"注册句柄被移除"严格绑定——数据泵、空闲回收器、关闭帧三方竞争清理时不会重复释放或泄漏，杜绝配额漂移导致的服务器假死。
* **半关闭语义正确**：客户端 FIN 只关闭发送方向，服务端响应可继续传完（WT 专用流与模式 A 复用通道行为一致；mux 客户端泵曾在此提前删除会话路由导致响应被丢弃，已修复并由 e2e 锁定）；只有 RST/协议错误/连接销毁才中止整条会话。
* **数据报自愈**：单个损坏的 QUIC 数据报只丢弃其缓冲即恢复解析，不影响后续帧（防重放滑动窗口保留，不因错帧重置）。
* **代理入站失败可见且可分类**：出口会话建立失败时，本地入站返回固定分类词——`dial-failed`、`session-limit`、`private-target-denied`、`bad-target`、`transport-failure`。SOCKS5 侧映射到 RFC1928 回复码（私网拒绝 `0x02`、拨号失败 `0x05`、其余 `0x01`）；HTTP 代理侧回 `502 Bad Gateway`，分类词同时出现在 `X-Newppp-Error` 响应头与正文。
* **错误分类，连接不被误杀**：服务端拒拨等目标侧错误不会触发重连 churn；连接池 `acquire` 跳过满载连接、维护循环裁剪空载超编连接，被退役的连接会**显式关闭** QUIC 会话（不会因后台任务持有连接克隆而泄漏到服务端）。
* 超时兜底：握手 10s、出口拨号 10s、降级 POST 响应头 30s、空闲会话按 `--idle` 回收。
* **两条独立的 30s 心跳，勿混淆**：
  * **WT 主路径应用层 Ping/Pong**：只要客户端配了 `--server` 就会发（与 `--url`/WSS 无关），经与服务器的 UDP 443 直连。作用：链路假死探测 + 刷新 NAT/运营商的 UDP 会话映射。**客户端校验 Pong**——连续 2 个心跳周期（约 60s）收不到 Pong 即判定链路半死（路由器重启、睡眠唤醒、NAT 换映射后 TCP 入站可能仍活着），主动关闭该连接、池自动重拨、降级链照常接管，避免下一请求"陪跑"握手超时。服务端回 Pong 但**不计入连接活性统计**——无会话的连接超 3×`--idle` 照样被回收重建，心跳不会扎住僵尸连接。这是主路径的必要设计，不参与降级静默。
  * **wss 兜底通道的 WS 层 Ping**：仅当 fallback 通道已建立时存在（防 Cloudflare 等中间件的空闲计时器掐断连接，免费版约百秒级）。只配 `--server` 时不存在此心跳。
  * 服务端 INFO `wt conn authenticated` 反复出现（常见成对）= 客户端连接死亡后池维护任务重拨（默认 `--conns 2` 顺序补两条），属自愈而非重复认证；客户端日志搜 `wt connection dead: <原因>` 可直接得到每条连接的死亡原因（QUIC 关闭原因 / 心跳 Pong 超时 / 控制流、数据报通道关闭 / 池主动退役）；先查服务端 `reaping idle conn` 日志排除空闲回收（设计行为），再查 UDP 链路质量（排查 checklist 见 [待办_新.md](待办_新.md)）。
* 连接池维护重拨**指数退避**：10s 起、上限 5min；但只要当轮拨通至少一条就重置——持续弱网下重拨保持密集重试形态。
* **回归安全网**（基线验收）：`tests/e2e.rs` 在单进程内以真实监听器 + 真实客户端栈驱动上述全部保证——降级链与熔断、错误分类、半关闭（WT 与模式 A 双路径）、>MTU UDP 落流、认证矩阵、私网策略、配额恰好一次释放、监听端口复用；熔断阈值/冷却为构造参数，测试传小值即可验证，无需真等 60s。CI（[.github/workflows/ci.yml](../.github/workflows/ci.yml)）执行 fmt/clippy/test 并在 tag 时产出 musl 二进制。

## 背压与容量

* 背压完全依赖 QUIC 流控（本地 TCP 阻塞 → 停读 → 对端停写），不做应用层流控
* 会话上限：客户端每连接 ≤ 50、服务端每连接 ≤ 64；连接池 1..8 条（自动补活）；全局会话上限 200（`--max-sessions`）
* 未认证连接上限（D1）：全局 `--max-unauth`（默认 128），WT 直连另按源 IP 限 1/8（2..64）；名额从接入持有到 AUTH 帧通过（或连接断开），认证后立即释放，故不挤占已认证会话
* 每用户令牌桶限速（`--rate` Mbps）：同一 uid 的所有连接共享一个桶，TCP 上/下行与 UDP 中转全部计入（0 不限）；空闲会话 60s 回收（`--idle`）；无会话且无数据活动的空连接 3×`--idle` 回收（keepalive Pings 不计入，服务端主动关闭 QUIC，客户端自动重连）；30s PING 保活
* 100 并发流 × 64KB 会话缓冲 ≈ 数十 MB 内存；1Gbps 下 ChaCha20 约占 1 核

## 浏览器指纹对齐与隐蔽性（F 系列，2026-09-14）

> 依据 Hysteria v2 源码调研 + wtransport/quinn/rustls 源码逐项探明，计划与结论见 [待办_新.md](待办_新.md) F-1~F-5。威胁模型分层：ISP 视角泄露的不是隧道内容（E2E 已保证）而是**隧道存在本身**——按信息量排序：DNS/SNI > 目的 IP > 握手指纹 > 流量形态。

### 客户端 QUIC/TLS 层对齐（主路径 WT）

| 项 | 实现 | 效果 |
|---|---|---|
| **源 CID** | 所有连接使用 8 字节 CID | 连接池可能在启动竞争或单连接达到会话上限时临时创建额外连接，因此优先保证 QUIC endpoint 能正确区分各连接 |
| **8 字节初始 DCID** | `ClientConfig::initial_dst_cid_provider`（8 字节） | quinn 默认 20 字节（MAX_CID_SIZE），首个数据报即显眼 |
| **TP 数值对齐** | `initial_max_data` 32MB（quinn 默认 VarInt::MAX≈2^62 任何浏览器都不会发）；关闭 DPLPMTUD（Chrome 默认不做 PMTUD，quinn 默认 600s 探测包本身是特征） | TP 数值型差异消除 |
| **TP 已一致项**（quinn 默认即 Chrome，不上线） | `max_idle_timeout=30s`、streams 100/100、`ack_delay_exponent=3`、`max_ack_delay=25ms`、`max_udp_payload_size=1472` | — |
| **GREASE ECH** | ClientHello 携带 `encrypted_client_hello` dummy 扩展（`EchMode::Grease` + 自建 HPKE 后端） | 与 Chrome 对无 ECH 服务器的行为一致；anti-ossification；对不支持 ECH 的服务器零交互 |

**TP 层不可消除的残留**（quinn 硬编码总是发送，无 setter）：`min_ack_delay`、`grease_transport_parameter`、`write_order`——消除需 fork quinn-proto，明确不做。被动观察者从 TP 表仍可判定"非 Chrome"，但对齐后可判定项显著减少。

### `conns` 与源 CID

客户端连接池大小影响物理连接数量，但不决定源 CID 长度：所有连接统一使用 8 字节源 CID，使同一 QUIC endpoint 上的多条连接可以被正确区分。源 CID 属于 QUIC 包头中的连接标识，不是证书、公钥，也不是内层加密内容；应用层数据流中的 `sid` 只能标识代理会话，不能替代 QUIC CID。

`conns = 1` 适合浏览、视频和低并发，`conns = 2` 适合多应用并发，代价是额外连接和心跳。初始 DCID 和源 CID 均为 8 字节。单条连接达到 50 个会话后，客户端可能临时创建额外连接，因此极高并发场景应使用 `conns = 2` 或更高。

**HPKE 后端**（`src/client/ech.rs`）：rustls 0.23 的 `ring` provider 无 HPKE 实现，用纯 Rust `hpke` crate 实现 `crypto::hpke::Hpke` trait——DHKEM(X25519, HKDF-SHA256) + HKDF-SHA256 + ChaCha20-Poly1305（Chrome 同款 suite），RFC 9180 往返测试覆盖。真实 ECH（SNI 加密，需 DoH 查 DNS HTTPS RR）留待后续（Backlog）。

### 流量形态层

* **心跳去周期化**：WT 主路径应用层 Ping 间隔 30s ± 20%（24..36s 均匀抖动）——固定间隔心跳是教科书式 beaconing 信号，被动观测者按周期性即可从 CDN 流量中筛出连接。Pong 判死预算不受影响（最坏连续 2 个周期为 36s × 2 = 72s，仍高于 60s）。
* **握手帧随机 padding**：AUTH 帧（WT + fallback 双路径）与 Open 帧 payload 尾部追加 `[64, 512)` 随机字节——握手密文长度不再是固定协议签名。**协议内兼容，服务端零改动**（解码按字段前缀解析，尾部自然忽略）。Data 帧不加：热路径性能敏感，且流式数据长度本身即真实形态。

### 直连路径 SNI 伪装 + 证书 pinning（F-6，`--sni` / `--pin`）

伪装域名不必是自己的域名、不必是 ECH——只需让 ISP 认为我们在访问某个它认识的域名（如 bilibili）：DNS 查伪装域名（正常用户行为，本身即掩护），SNI=伪装域名，**自己的域名从链路上彻底消失**（原来明文出现两次：DNS + SNI）。

* **机制**：URL host 被伪装名替换（驱动 TLS SNI 与 WebTransport `:authority`），连接地址由固定地址 resolver 指向原始 URL 的 host:port——SNI 与拨号地址天然解耦。WT 路径走 wtransport `DnsResolver`，fallback POST 路径走 hyper `Service<Name>` resolver；
* **证书 pinning 替代 CA 校验**（`--pin <sha256>`）：伪装名下服务器证书不可能匹配 SNI，CA 校验必挂——改为校验"对端证书 SHA-256 == pin 值"（恒时比较）。对私人代理这**比公共 CA 校验更强**：无签发链风险，服务器身份就是那枚指纹；签名验证仍走标准算法（握手密码学不变，仅替换信任锚决策）；
* **服务端零改动**：wtransport 单 Identity 对 SNI 无感知；协议层（认证帧/bearer）不含域名；向后兼容（不配 `--sni` 行为不变）；
* **收益边界**：这是"去明文化"不是隐身——IP 锚点不动（被动 DNS 库仍知道 VPS IP 的历史解析）；SNI-IP 一致性检查（境外 IP + 国内热门域名）在交叉分析下反而可疑，伪装域名选型须境外热门 + 支持 h3/QUIC + 与托管地区合理共存；**最强形态是无域名部署**（VPS 不发布 A 记录 + URL 写 IP + `--pin` 唯一锚点）；
* **适用范围**：仅直连路径；`--sni` + `wss://` 报错拒绝（CF 按真实 SNI 路由回源）。指纹获取与轮换操作见 [手册.md](手册.md#pin-指纹获取与轮换)。

### 明确不做（已定性）

* **ChromeParrot 等效物**（完整 ClientHello 伪装）：quinn 把握手外包给 rustls，需同时 fork 两层——Hysteria 能做是因 quic-go 自带 TLS 握手（fork 一层即可），Rust 分层架构无此条件。
* **Salamander / Gecko 式 UDP 层混淆**：quinn runtime 接管 socket I/O 循环，不支持逐包变换；且 Salamander 与"过 CDN"主形态冲突。

## 隐私与安全模型

**密码学底线两条路径等价**：所有代理帧（目标地址、payload、UDP 数据）都在内层 E2E 加密里（ChaCha20-Poly1305 + 每连接随机 salt 派生的会话密钥）——**CF 在任何情况下只能看到密文帧**，这是架构保证，不依赖 CF 的善意。"隐私"的差异在元数据层：

### wss + CF（橙云）

| 维度 | 状况 |
|---|---|
| 内容机密性 | ✅ E2E 层保证，CF 解不开帧 |
| CF 能看到 | ⚠️ SNI/域名、**Bearer 头里的 uid（明文）**、流量大小/时序/时长 |
| CF 看不到 | ✅ 目标主机、payload、DNS 查询、UDP 目标 |
| 信任代价 | ⚠️ CF 是"合法中间人"：受法律强制、可记录审计——等于多信任一方 |
| 附带收益 | ✅ 源站 IP 隐藏、L3/L4 DoS 由 CF 吸收、IP 不进 DNS 历史 |
| 隐蔽性风险 | ⚠️ 长连 WS 双向二进制流是可指纹的代理模式；CF 可挑战/限流；免费版无 SLA |

### 直连 UDP（灰云）

| 维度 | 状况 |
|---|---|
| 内容机密性 | ✅ 同样靠 E2E 层；QUIC-TLS 端到端（自己的证书，无中间人） |
| 元数据 | ✅ 无第三方中间人，只有两端 ISP 能看到"有 QUIC 流量到某 IP" |
| 最大弱点 | ❌ **源站 IP 公开**：域名直接解析到 VPS，DNS 历史会永久暴露 |
| 隐蔽性 | ⚠️ 指纹已对齐浏览器（零长度 CID、TP、GREASE ECH、心跳抖动，见上文「浏览器指纹对齐」），但 TP 结构性残留（min_ack_delay 等）仍可被深度分析判定；跨境 UDP 常被 QoS/阻断（弱网 `too many gaps` 即此现实） |
| DoS 面 | ❌ 源站直接暴露，L3/L4 攻击自己扛 |

### 两条路径共同的真实弱点（比选路更重要）

1. **密钥根是 `HKDF(password)`，不是慢哈希 KDF**（无 Argon2/PBKDF2）。攻击者捕获 bearer/AUTH 材料后可**离线爆破弱密码**——密码必须强随机，这是整个体系真正的根。
2. 服务器本身知道一切（目标、流量），自建节点的固有边界，与传输无关。
3. `--skip-verify` 只限调试；生产两条路径都走真实证书链，服务器身份验证完整。

### 取舍结论

* **内容机密性**：两者等价，前提是密码够强。
* **元数据隐私**：直连略优（无中间人），代价是 IP 暴露 + 指纹/阻断风险（指纹已大幅对齐，见「浏览器指纹对齐与隐蔽性」）。
* **抗封锁/隐蔽性**：wss+CF 优（探测面只有一个普通网站）。
* 组合方案见档位 2：灰云子域跑 WT 主路径 + 橙云 wss 兜底。

## 性能（帧热路径）

每帧的加密与封装是代理吞吐的核心。`benches/frame.rs`（criterion）对 64B / 1KB / 16KB 负载分别测量裸 AEAD 与整帧编解码；生产路径已改为**单次分配 + `encrypt_in_place`**（`FrameCipher::seal_slice`、`FrameEncoder::encode_into`，`FrameWriter` 复用 `BytesMut`）：

| 场景（16KB 帧） | 优化前 | 优化后 |
|---|---|---|
| `frame/encode` | 17.34 µs | **13.31 µs（−23%）** |
| `frame/decode` | 15.86 µs | **13.47 µs（−15%）** |
| 裸 `aead/seal`（对照） | 14.63 µs | 13.26 µs |

整帧 encode 已与裸 AEAD 持平，说明封装/分配开销基本消除。1Gbps（≈7600 帧/s @16KB）下该路径约 10% 单核占用。
