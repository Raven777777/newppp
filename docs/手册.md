# newppp 手册

使用手册：部署形态、快速开始、服务端与客户端参数。

> 本文档由根目录 [README.md](../README.md) 拆分而来。生产部署与运维见 [运维手册.md](运维手册.md)，协议与安全模型见 [协议文档.md](协议文档.md)。

## 部署形态

### 形态 A：完整形态（默认）

服务端监听 UDP 443（WebTransport 主路径）+ TCP 443（降级/伪装站）+ 80（301 门面）。客户端带 `--server` 与 `--url`，WT 不可用时自动落到降级通道。性能最优。

### 形态 B：纯网站形态（隐蔽切换）

把流量全部收敛到 `/api/ppp`（TCP 443 的模式 A 通道），TCP/UDP 代理都从这条双工 POST 走：

- 客户端只传 `--url`，去掉 `--server` —— 不碰 UDP；
- 服务端**省略 `--listen`** —— UDP 443 完全不监听，机器上不存在 UDP 套接字，**无需任何防火墙规则**。

服务端形态 B 示例：

```bash
newppp -s --auth alice:secret123 \
  --fallback-listen 0.0.0.0:443 \
  --http-listen     0.0.0.0:80 \
  --cert ./_.love4z.cn.pem --key ./_.love4z.cn.key
```

形态切换只改启动参数，密钥与 `/api/ppp` 不变。

### 形态 B-CF：Cloudflare 橙云变体

Cloudflare 标准代理会**缓冲完整请求体后才回源**（免费 100MB 上限同理），无限长的双工 POST 永远等不到结束 → 请求根本到不了源站；WT 主路径也不可行（CF 在边缘终止 h3，QUIC 不透传）。因此套 CF 必须换 WebSocket 承载：

- 客户端 `--url wss://newppp.love4z.cn/api/ppp`（scheme 由 https 换成 wss）；
- 服务端不变（`/api/ppp` 同时接受 POST 与 WS 升级，认证流程相同）；
- CF 侧无需任何配置（免费版完整支持 WebSocket，双向流式、无体积上限）；
- 内置 30s WS 层心跳防 CF 空闲断连。

**形态 B 的性能代价**：UDP 包改走可靠有序的 TLS 流，丢包会队头阻塞——DNS/普通请求无感（实测 DNS ~170ms），游戏等实时 UDP 受损。按威胁模型与用途选择形态，或随时切换。

**探测面的三层账**（为什么形态 B 更隐蔽但不"隐身"）：

| 探测层 | 形态 A (WT) | 形态 B (/api/ppp) |
|---|---|---|
| 端口扫描 | UDP 443 暴露"QUIC 服务" | ✅ 只有一个 TLS 网站端口（UDP 不监听，连"被过滤端口"的痕迹都没有） |
| 协议指纹 | QUIC 层已对齐浏览器（零长度 CID、TP、GREASE ECH，见 [协议文档.md](协议文档.md#浏览器指纹对齐与隐蔽性f-系列2026-09-14)），但 TP 结构性残留仍可被深度分析判定 | ✅ 无 QUIC 可探测 |
| 流量形态 | 长连接多流（像视频/云盘），心跳已去周期化（±20% 抖动） | 无限长双向 POST/WS（内容级分析仍可标记）|

### 域名路由速查：走不走 CF 看云朵，不看 scheme

CF 路由由域名的 **DNS 代理状态**决定（橙云=代理、灰云=仅 DNS 直连）；`https://` / `wss://` 只是承载方式（双工 POST / WebSocket），与是否经过 CF 无关：

| 配置 | 实际走向 | 可用性 |
|---|---|---|
| `--url https://灰云域/api/ppp` | 直连 VPS | ✅ 速度最优的 POST 兜底 |
| `--url wss://灰云域/api/ppp` | 仍直连（wss 不会"激活"CF） | ✅ 与上行等价 |
| `--url https://橙云域/api/ppp` | 走 CF | ❌ CF 缓冲完整 POST 请求体才回源，双工 POST 永远到不了源站 |
| `--url wss://橙云域/api/ppp` | 走 CF | ✅ 橙云下唯一可用承载（WS 不被缓冲，免费版完整支持） |
| `--server` 指向橙云域 | WT 会话在 CF 边缘被终止 | ❌ CF 不透传 QUIC/WebTransport，主路径必须灰云域 |

**推荐组合**：`--server https://灰云域`（WT 主路径保带宽）+ `--url https://灰云域/api/ppp`（直连 POST 兜底，远快于经 CF）；仅当需要隐藏源站 IP 时，才把兜底换成 `--url wss://橙云域/api/ppp`（代价是 CF 免费版链路可能很慢，实测有低至 ~50KB/s 的情形）。

## 快速开始

### 服务端（单进程全链路，自签调试）

```bash
newppp -s --auth alice:secret123 --self-signed \
  --listen          0.0.0.0:443 \
  --fallback-listen 0.0.0.0:443 \
  --http-listen     0.0.0.0:80
```

其中 `--listen` 是 UDP WebTransport 主路径，`--fallback-listen` 是 TCP
伪装站与降级 API，`--http-listen` 是可选的 301/ACME 门面。

* UDP 443 与 TCP 443 不冲突，一个进程全占；防火墙放行 UDP 443 / TCP 443 / TCP 80。
* 80 端口是纯门面：一切请求 301 → `https://同Host/原路径`（带 HSTS），明文 API 已关闭。
* `--acme-dir /var/www/acme` 可选：在 80 上服务 Let's Encrypt http-01 验证文件（`certbot certonly --webroot -w /var/www/acme -d your.domain`），token 白名单校验防路径穿越。
* 未认证访问 443 伪装站与降级端点，得到的都是 nginx 欢迎页风格的 200 页面。
* 服务端默认拒绝代理用户访问回环、私网、链路本地、metadata 等非公网目标；本地联调或明确的内网代理场景才使用 `--allow-private-targets`。

### 客户端

```bash
newppp -c --auth alice:secret123 \
  --server https://your.domain:443 \
  --url https://your.domain/api/ppp \
  --bind 127.0.0.1:1080 --http-bind 127.0.0.1:8081
```

* `--server` 与 `--url` 至少配一个；两者都配时 WT 优先、失败自动降级（连续传输层故障会熔断主路径一段时间，见 [协议文档.md](协议文档.md#降级链)）。
* **形态 B（纯网站形态）**：去掉 `--server` 只留 `--url`，并使用省略 `--listen` 的服务端（见上）；套 Cloudflare 时 `--url` 换成 `wss://`（见形态 B-CF）。
* 自签调试加 `--skip-verify`；换成 Let's Encrypt 证书后**去掉**该参数（走系统根证书校验）。
* **低频用户建议加 `--conns 1`**：日常浏览/视频/下载的会话模式一条 QUIC 连接完全够用（每连接上限 50 会话），代价最小心跳/重拨 churn；重度多任务场景保持默认 2。
* 绑 `0.0.0.0`（NAS/局域网共享）时建议加 `--inbound-auth user:pass`：SOCKS5 走 RFC1929 用户名/密码、HTTP 代理走 Basic Auth，凭证用常量时间比较；不配则本地入站无认证。

### 验证

```bash
curl --socks5-hostname 127.0.0.1:1080 https://www.google.com
curl -x http://127.0.0.1:8081 https://www.google.com

# 启用 --inbound-auth user:pass 后：
curl --socks5-hostname user:pass@127.0.0.1:1080 https://www.google.com
curl -x http://user:pass@127.0.0.1:8081 https://www.google.com
```

自动化回归：`cargo test --all-features` 跑单元/property 测试 + `tests/e2e.rs` 的进程内端到端（真实 server+client：降级链/熔断、认证矩阵、半关闭、UDP、私网策略、生命周期收尾、优雅停机、端口复用），CI 自动执行（见 [.github/workflows/ci.yml](../.github/workflows/ci.yml)）。服务端/客户端的行为断言细节见 [协议文档.md](协议文档.md#会话生命周期与稳健性)。

## 配置文件（--config）

把一长串命令行参数搬进文件：`--config /path/newppp.conf` 显式指定（文件不存在直接报错退出）；不带 `--config` 时，**当前工作目录下的 `newppp.conf` 若存在则自动加载**，不存在则行为不变。

格式（键名就是命令行的**长选项名原样**，无独立词汇表）：

```
# 注释行；空行忽略
mode = server                 # server | client（也可在命令行用 -s/-c）

auth  = 2233:mvNn...          # 同 key 多行 = 多用户叠加
auth  = bob:hunter2

listen          = 0.0.0.0:443
fallback-listen = 0.0.0.0:443
http-listen     = 0.0.0.0:80
cert            = /etc/newppp/cert.pem
key             = /etc/newppp/key.pem
max-sessions    = 200

# 布尔开关：整行只写键名（也可写 key = true）
self-signed
```

规则：

* **优先级：命令行 > 配置文件**（临时改一两项不用动文件）；同一文件里靠后的行覆盖靠前的；
* 值**成对包裹的引号会被剥离**（`'…'` / `"…"`），引号之后的内容当注释；不包裹的值**原样保留**（`#`、空格都是值的一部分，如 URL 带 `#` 于引号中）；
* 缺了值（`listen =`）、未知 key、布尔开关带了值 → 报错并指出文件与行号，先于监听退出（P2-3）；
* `--cert/--key` 的**文件存在性**在启动期校验（P2-3），路径打错直接报错退出；
* **凭据卫生**（P2-1/P2-2）：含 `auth` 行的文件，权限过宽（group/other 可读）时启动 WARN 并提示 `chmod 600`；Docker 场景改挂载配置文件（Cmd 烧 `--config /etc/newppp/newppp.conf`），`docker inspect` 里不再有密码。

## 服务端参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--auth` | 必填 | `user:pass`，可重复注册多用户（uid 限 `[A-Za-z0-9_-]{1,32}`） |
| `--config` | - | 配置文件（键=长选项名，见上文「配置文件」节）；未给时自动探测工作目录 `newppp.conf` |
| `--time` | https://www.cloudflare.com/cdn-cgi/trace | 内部时钟的时间源 URL（HTTP Date 头校准，客户端+服务端均可用，见 [协议文档.md](协议文档.md#内部时钟http-date-校准)） |
| `--listen` | - | WebTransport (QUIC/UDP) 监听；**省略则完全不监听 UDP**（形态 B 纯网站形态）。注意：提供时仅端口生效，IP 部分被忽略（总是绑定全部接口） |
| `--cert/--key` | - | TLS PEM（或 `--self-signed` 自签调试） |
| `--fallback-listen` | - | TLS TCP 降级/伪装站监听（模式 A POST + WebSocket 双承载） |
| `--http-listen` | - | 80 门面：301 → https + 可选 ACME 验证（明文 API 不可用） |
| `--acme-dir` | - | certbot http-01 验证文件目录 |
| `--path` | /api/ppp | 降级端点路径 |
| `--max-sessions` | 200 | 全局并发会话上限 |
| `--max-unauth` | 128 | 全局并发**未认证**连接上限（已接入但尚未通过 AUTH 帧）；每源 IP 上限为其 1/8（2..64，WT 直连按源 IP 计，降级请求在 CDN 后仅计全局）。超限连接被静默拒绝，不影响已认证连接 |
| `--allow-private-targets` | off | 允许访问回环、私网、链路本地及其他非公网目标；仅用于本地联调或明确的内网代理场景 |
| `--rate` | 100 | **每用户**限速 Mbps（0 不限）：同一 uid 的全部连接共享一个令牌桶，覆盖 TCP 上/下行与 UDP 中转全部流量；桶容量为 1 秒的量（短时突发最多预存 1s，不同连接不能叠加配额） |
| `--idle` | 60 | 空闲会话回收秒数 |
| `--recv-window` | 2 | QUIC 每流接收窗口 MB（1..=64，上传方向） |
| `--health` | - | 健康端点监听（明文 HTTP，建议仅回环）：`/healthz` JSON 运行时快照，供 docker HEALTHCHECK / NAS 管理器探测（见 [运维手册.md](运维手册.md#健康检查--health-与-healthcheck-子命令)） |
| `--shutdown-grace` | 10 | 优雅停机排空在途会话的秒数，超时强杀（配合 systemd `TimeoutStopSec`） |
| `--log` | info | 日志级别（trace/debug/info/warn/error） |

## 客户端参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--auth` | 必填 | `user:pass`（取第一组） |
| `--config` | - | 配置文件（同服务端，见上文「配置文件」节）；客户端凭据同样可搬进文件 |
| `--time` | https://www.cloudflare.com/cdn-cgi/trace | 内部时钟的时间源 URL（HTTP Date 头校准，见 [协议文档.md](协议文档.md#内部时钟http-date-校准)） |
| `--server` | - | WT 服务端 URL（https://host[:port][/path]） |
| `--url` | - | 模式 A 降级 URL，scheme 决定承载：`https://`（双工 POST，直连用）或 `wss://`（WebSocket，套 Cloudflare 必用）；与 `--server` 至少配一个 |
| `--bind` | 127.0.0.1:1080 | SOCKS5 监听（CONNECT / UDP ASSOCIATE） |
| `--http-bind` | - | HTTP 代理监听（CONNECT + 简单转发，出口失败回 502） |
| `--inbound-auth` | - | 本地入站认证 `user:pass`：SOCKS5 RFC1929 用户名/密码 + HTTP 代理 Basic Auth；不配则无需认证（绑 `0.0.0.0` 时建议启用） |
| `--conns` | 2 | 连接池大小（1..8）。**低频用户（浏览/视频/下载）建议 `--conns 1`**：一条 QUIC 连接每连接可承载 50 条会话完全够用，默认 2 的收益仅是并发冗余，代价是心跳与重拨开销 ×2；重度多任务/多应用共享代理时再显式 `--conns 2` |
| `--sni` | - | **伪装 SNI**（直连路径专用）：TLS ClientHello 的 SNI 与 DNS 查询目标换成该域名，实际连接地址取自原始 URL。须配合 `--pin`（或调试用 `--skip-verify`）。选型建议：境外热门 + 支持 h3/QUIC 的域名；与 `wss://` 兜底互斥（CF 按真实 SNI 路由）。**最强形态**：URL 直接写 IP + `--pin` 唯一锚点——自己的域名完全不出现在链路上 |
| `--pin` | - | **证书指纹 pinning**（SHA-256，64 hex，容忍冒号分隔）：设置后完全替代 CA 校验，服务器身份 = 这枚证书。比公共 CA 校验更强（无签发链风险）。与 `--skip-verify` 互斥。获取方法见下「`--pin` 指纹获取」；**证书轮换后指纹即失效**（见同节） |
| `--recv-window` | 2 | QUIC 每流接收窗口 MB（1..=64，下载方向）：优质高延迟线路可调大提速，高丢包调小抗 `too many gaps`。注意：该值同时决定 `initial_max_stream_data` TP——调大偏离浏览器常见值，指纹敏感部署保持 2 |
| `--health` | - | 健康端点监听（明文 HTTP，建议仅回环）：`/healthz` JSON（含 `circuit` 熔断状态与 `last_fallback_at` 兜底时刻），供 docker HEALTHCHECK 探测 |
| `--skip-verify` | off | 跳过证书校验（仅调试） |
| `--log` | info | 日志级别（trace/debug/info/warn/error） |

另有独立子命令 `newppp healthcheck --url http://127.0.0.1:9100/healthz`：一次性探测，退出码 0/1（docker HEALTHCHECK 用）。

### 客户端内置的浏览器指纹对齐（无需配置）

客户端 QUIC/TLS 层默认对齐 Chrome（零长度源 CID、8 字节初始 DCID、TP 数值、GREASE ECH 扩展），心跳已去周期化——详见 [协议文档.md](协议文档.md#浏览器指纹对齐与隐蔽性f-系列2026-09-14)。无任何 CLI 开关，行为始终开启；`--recv-window` 是唯一会改变 TP 数值的用户可调项。

### `--pin` 指纹获取与轮换

指纹 = 服务端 TLS 证书（对端握手出示的那张）的 SHA-256 摘要，64 位 hex（冒号分隔格式同样接受）。

**获取方法**：

```bash
# 方法 1：在服务器上对部署用的证书文件执行（最常用）
openssl x509 -in /etc/newppp/cert.pem -noout -fingerprint -sha256
# 输出 sha256 Fingerprint=AB:CD:EF:... —— 去冒号（或保留）即 --pin 值

# 方法 2：--self-signed 模式 —— 证书在服务器临时目录，
# 启动 WARN 日志会打印路径，到该路径执行同样的命令

# 方法 3：不碰服务器，从客户端机器对 fallback 端口（TCP 443）抓取
openssl s_client -connect your.server:443 -servername your.domain </dev/null 2>/dev/null \
  | openssl x509 -noout -fingerprint -sha256
```

注意方法 3 只对 TCP 端口有效（WT 主路径是 QUIC/UDP，openssl s_client 不支持）；但 WT 与 fallback 共用同一张证书，指纹一致。

**pin 的是哪张证书**：

| 部署形态 | pin 的对象 |
|---|---|
| 纯 newppp 进程监听 | `--cert/--key` 指向的 PEM（或 `--self-signed` 生成的） |
| 档位 1（nginx 终止 TLS 反代） | **nginx 用的证书**（客户端握手对端是 nginx，不是 newppp 的证书） |

**轮换提醒（重要）**：`--pin` 锚定的是这一张证书——换证书（Let's Encrypt 续期、重新自签）后指纹变化，客户端全部拒绝连接（报 `certificate fingerprint mismatch (--pin)`）。因此：

* 自签 / 长有效期证书场景：证书静态、指纹静态，`--pin` 是理想搭配（正是 `--sni` 伪装的预期组合——伪装名下证书不可能匹配域名，LE 自动续期与 pinning 天然矛盾）；
* 需要 Let's Encrypt 自动续期的部署：**不要用 `--pin`**，继续走 CA 校验，也不要配 `--sni`（伪装与 LE 证书互斥，见 `--sni` 行说明）；
* 轮换证书时的操作顺序：服务器换证书 → 重新计算指纹 → 更新各客户端配置文件中的 `pin = ...` → 重启客户端（降级链会让会话平滑迁移）。

### 本地入站的失败分类

出口会话建立失败时，本地入站会带**固定分类词**返回，便于脚本断言与排障：

| 分类词 | 含义 | SOCKS5 回复码 | HTTP 代理 |
|---|---|---|---|
| `dial-failed` | 服务端拨号失败 | `0x05` | `502` + `X-Newppp-Error: dial-failed` |
| `session-limit` | 会话/连接限额 | `0x01` | `502` + `X-Newppp-Error: session-limit` |
| `private-target-denied` | 默认策略拒绝私网目标 | `0x02` | `502` + `X-Newppp-Error: private-target-denied` |
| `bad-target` | 目标非法 | `0x01` | `502` + `X-Newppp-Error: bad-target` |
| `transport-failure` | 传输层故障（降级前） | `0x01` | `502` + `X-Newppp-Error: transport-failure` |
