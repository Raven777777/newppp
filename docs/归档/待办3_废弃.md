## 使用约定

1. **归属**：新任务必须落在「连通 / 生命周期 / 可维护 / 隐蔽性」四者之一，否则进 Backlog。
2. **触发条件**：Backlog 条目必须写清"观察到什么现象才启动"，没有触发条件的需求直接拒绝。
3. **验收即完成**：每项的完成标准是一条能跑的命令或一个具名测试，不写形容词。
4. **顺序**：按优先级执行；Backlog 不占带宽，只有触发条件命中才启动。

## 待办

### F：指纹与隐蔽性（借鉴 Hysteria v2 源码调研结论，2026-09-13）

> 调研对象：hysteria-master（apernet/hysteria）core 源码。关键发现：
> ① 其 Chrome 指纹伪装在 **fork 版 quic-go 内部**（`ChromeParrot` + `ZeroLengthConnectionIDGenerator`），**不是 uTLS**——印证"伪装 ClientHello 的前提是 TLS 栈归我管"，Rust 生态（quinn+rustls 分层）无等效低成本路径，**明确不做**；
> ② **零长度源 CID** 是 Chrome 标志性特征，明文暴露在**每个 UDP 包头**，比 TP 更显眼、比 JA3 更易提取——最高性价比；
> ③ ECH 客户端/服务端双端支持（Go 生态现成）；
> ④ 流量形态层工具箱：Gecko（仅握手包随机分片+padding）、Salamander（UDP 层 XOR 混淆，不能过 CDN）、应用层自适应 padding、PMTUD 按平台禁用。
>
> 威胁模型分层结论（本轮讨论确定）：ISP 视角下泄露的不是隧道内容（E2E 已保证）而是**隧道存在本身**——按信息量排序：DNS/SNI > 目的 IP > 握手指纹 > 流量形态。**指纹对齐只在域名与 IP 都隐藏（走 CF wss）之后才有价值**；未认证访客走浏览器拿伪装页属无辜噪声，对掩护是正贡献，暴露面集中在自用客户端链路。

- [x] **F-1 零长度源 CID（客户端）+ 8 字节初始 DCID** — 最高性价比，**已探明可行，✅ 已落地（2026-09-14）**
  - 探明结论（2026-09-14，wtransport 0.7.2 + quinn-proto 0.11.17 源码核实）：
    * wtransport 构建后的 `ClientConfig` / `ServerConfig` 均公开 `quic_endpoint_config_mut()`（feature "quinn"，本项目已启用）→ 直通 quinn `EndpointConfig::cid_generator()`，自定义 `ConnectionIdGenerator`（`cid_len()=0`、`generate_cid()` 返回空 `ConnectionId`）即可实现零长度 SCID——quinn-proto 自带的 `RandomConnectionIdGenerator::new(0)` 即可用（`ConnectionId::new(&[])` 仅 debug_assert 上限，0 长度合法）；
    * **意外发现**：quinn 客户端 Initial 包的 DCID 默认 `RandomConnectionIdGenerator::new(MAX_CID_SIZE)` = **20 字节随机**，Chrome 是 8 字节——首个 UDP 包即肉眼可辨的差异。`quinn::ClientConfig::initial_dst_cid_provider()`（wtransport `quic_config_mut()` 直通）可改为 8 字节。
  - 做法：`build_tls_config()` 构建后调用 `quic_endpoint_config_mut().cid_generator(...)`（零长度 SCID）+ `quic_config_mut().initial_dst_cid_provider(...)`（8 字节 DCID）。服务端不动（服务端 SCID 形态本就与 Chrome 无关，Chrome 作为客户端只关心自己的 SCID=0）。
  - 验收：抓包确认客户端 Initial 包 SCID 长度 0、DCID 长度 8；e2e 全绿（✅ `socks5_connect_and_udp_associate_over_wt` 等真实 WT 连接全部通过）。
  - 债：D1

- [x] **F-2 传输参数对齐 Chrome（客户端为主）** — **✅ 已落地可设项（2026-09-14），残留已定性**
  - 探明结论（quinn-proto 0.11.17 `config/transport.rs` + `transport_parameters.rs`）：
    * **可设**（`QuicTransportConfig` 公开 setter，wtransport 类型别名直通 quinn）：`max_idle_timeout`（默认已 30s）、`receive_window`（=initial_max_data）、`stream_receive_window`、`max_concurrent_bidi/uni_streams`（默认已 100/100）、`initial_mtu`/`min_mtu`/`mtu_discovery_config`、`datagram_receive/send_buffer_size`、`max_udp_payload_size`（挂在 EndpointConfig，默认已 1472）；
    * **不可设（结构性指纹，quinn 硬编码、无 setter）**：**总是发送** `min_ack_delay`（Chrome 不发）、`grease_transport_parameter`（Chrome 不发 GREASE TP）、`write_order`（quinn 私有扩展，Chrome 必无）——这三者是 TP 层最响亮的"我是 quinn"信号；`active_connection_id_limit` 硬编码（非零 CID 时=5，零长度 CID 时=2 不发送）。
    * **修正**：`ack_delay_exponent` 派生自 `TransportParameters::default()` = **3，与 Chrome 一致**且因等于默认值而不发送（此前误判为 2）；`max_ack_delay` 同理默认 25ms 不发送。
  - 结论修正：TP 对齐只能消除"数值型"差异（窗口/超时），**消除不了"扩展存在性"差异**。F-1（零 CID）顺带把 active_connection_id_limit 归位为 Chrome 同款"不发"。残留指纹 = min_ack_delay + grease TP + write_order，唯一消除路径是 fork quinn-proto（归入"暂不做"）。
  - 落地内容（`quic_tune.rs`）：`receive_window`（initial_max_data TP）从 quinn 默认 VarInt::MAX（≈2^62，任何浏览器都不会发）改为 32MB；`mtu_discovery_config(None)` 关闭 DPLPMTUD（Chrome 默认不做 PMTUD，quinn 默认开 600s 探测——探测包本身是特征）。`stream_receive_window`/`send_window` 保持 `--recv-window` 用户可调（弱网调参优先于指纹）。
  - 验收：e2e 全绿（TP 是协商字段，两端不必一致，无兼容风险）。
  - 债：D1

- [x] **F-4 应用层随机 padding（协议内兼容）** — ✅ 已落地（2026-09-14）

- [x] **F-5 GREASE ECH（客户端）** — **✅ 已落地（2026-09-14）**；真实 ECH 留待后续
  - 探明结论（rustls 0.23.44 源码核实）：
    * rustls 0.23.44 **内置 ECH**（非 feature gate）：`ConfigBuilder::with_ech(EchMode)`，支持真实 ECH（`EchMode::Ech(EchConfig)`，需从 DNS HTTPS RR 取 ECHConfigList）与 GREASE ECH（`EchMode::Grease(EchGreaseConfig)`）；
    * **缺口**：`ring` provider 无 HPKE 实现（rustls 只在 aws-lc-rs 后端有 `crypto::aws_lc_rs::hpke`），切换 provider 会改变整个加密栈且 aws-lc-sys 交叉编译 musl 不可行；
    * **解法**：新增 `src/client/ech.rs`——用纯 Rust `hpke` crate（RustCrypto，X25519+HKDF-SHA256+ChaCha20-Poly1305，Chrome 同款 suite）实现 rustls 的 `crypto::hpke::Hpke` trait，约 200 行胶水。
  - 落地内容：`build_tls_config()` 改为完全自建 rustls ClientConfig（`with_ech` 必须在 builder 阶段调用，rustls 0.23 无 post-hoc 重写 API），插入 `EchMode::Grease`；ALPN 显式设为 `WEBTRANSPORT_ALPN`（与 wtransport 原生行为一致）。
  - 效果：ClientHello 携带 `encrypted_client_hello` GREASE 扩展（与 Chrome 对无 ECH 服务器的行为一致）——中间盒必须容忍该扩展（anti-ossification），ClientHello 与浏览器又近一步；对不支持 ECH 的服务器零交互（外层 SNI 照常）。
  - 后续（真实 ECH）：已升级为正式待办 **F-6**（见下）。
  - 验收：✅ `seal_open_roundtrip_via_trait` / `context_seal_open_roundtrip` / `suite_ids_match`（HPKE trait 面 RFC 9180 往返）+ e2e 全绿（GREASE 扩展被自有 rustls 服务端正常接受）。抓包确认 `encrypted_client_hello` 扩展存在（部署后人工核验）。
  - 债：D1 上游（SNI 是 ISP 视角信息量最大的缺口）

- [x] **F-6 直连路径 SNI 伪装 + 证书 pinning（客户端）** — **必要项（2026-09-14 定级，取代原"真实 ECH"方案）**
  - **方案变更记录**：原方案为"DoH + 真实 ECH（仅 CF 橙云路径）"。讨论后改向：伪装域名**不必是自己的域名、不必是 ECH**——只需让 ISP 认为我们在访问某个它认识的域名（如 bilibili）。DNS 查伪装域名，实际连接自己的 IP（私人代理，IP 自知）。**ECH 相关条目（原 F-6 真实 ECH + DoH）废弃**——ECH 依赖 CF 配合 + DNS HTTPS RR 发布 + DoH 前置，运维链长；SNI 伪装服务端零改动、约 F-5 量级代码。
  - **动机**：直连路径（灰云 WT / 直连 POST）链路上域名明文出现两次（DNS 查询 + ClientHello SNI）。SNI 伪装后：DNS 查伪装域名（正常用户行为，本身即掩护）、SNI=伪装域名、**自己的域名从链路上彻底消失**。
  - **技术管道（已探明可行）**：
    * WT 路径：wtransport `ClientConfigBuilder::dns_resolver(R)` 是公开 API（`DnsResolver` trait）——URL host 取 SNI（伪装域名），resolver 把它解析到 VPS IP，两者天然解耦；
    * fallback POST 路径：hyper `HttpConnector` 支持自定义 resolver（`set_resolver`/`GaiResolver` 替换），同模式；
    * 服务端零改动：wtransport 单 Identity 配置对 SNI 无感知；协议层（认证帧/bearer）不含域名。
  - **关键设计：证书 pinning 替代 CA 校验**——SNI=伪装域名时服务器证书与 SNI 必然不匹配，CA 校验必挂。新增 `--pin <证书指纹>`（SHA-256 hex）：客户端校验"对端证书 == 认知中服务器的证书"，与 SNI 无关。对私人代理这**比公共 CA 校验更强**（无 CA 签发失误风险，服务器身份就是那枚指纹）。裸 `--skip-verify` 不再是伪装场景的选项（主动中间人可劫持握手）。
  - **CLI**：`--sni <域名>`（伪装 SNI + DNS 查询目标；缺省 = 现行行为，SNI=真实 URL host）；`--pin <指纹>`（设置后替代 CA 校验，与 `--skip-verify` 互斥报错）。两参数客户端 only，进配置文件（键 = 长选项名，现有机制自动支持）。
  - **边界与陷阱**：
    * IP 锚点不动：被动 DNS 库仍知道 VPS IP 的历史解析记录——这是"去明文化"不是隐身；
    * **SNI-IP 一致性**：境外 IP + 国内热门域名（bilibili）组合在 GFW 级交叉分析下反而可疑。伪装域名选择逻辑：境外热门 + 支持 h3/QUIC（我们走 QUIC，伪装对象最好真提供 h3）+ 与 VPS 托管商/地区合理共存。默认值选型在实现时定，文档给选型指南；
    * **最强形态是无域名部署**：VPS 不发布 A 记录 + 客户端 URL 直接写 IP + `--pin` 唯一身份锚点 + `--sni` 任意伪装域名——SNI-IP 交叉检查无从下手。代价：IP 变更需手动通知客户端（私人使用可接受）。文档给部署指南；
    * 档位 1（nginx 终止 TLS）：SNI 变化后现有 server 块不匹配——需加 catch-all default server（文档说明）；纯 newppp 进程监听无此问题；
    * CF wss 路径不适用也不需要（CF 靠真实 SNI 路由回源）——`--sni` 仅作用于直连路径，`--url wss://` 时报错拒绝（防误配）。
  - **实现要点**：
    * SNI 覆盖在 rustls 层做（`ServerName` 与 URL host 解耦），resolver 层做 IP 重定向——两处都集中在 `build_tls_config` / connector 构建点；
    * pinning 用 rustls `danger::ServerCertVerifier` 自定义实现（F-5 已有 `NoVerify` 同位替代品，改为"校验 SHA-256 指纹"而非"全接受"）；
    * GREASE ECH 保留（与 SNI 伪装正交：ECH 扩展形态对齐 + 伪装域名场景下 ECH 是 Chrome 常态行为）。
  - **运维边界（落地时补充）**：
    * 指纹获取：`openssl x509 -in cert.pem -noout -fingerprint -sha256`（或从客户端对 TCP 端口 `openssl s_client` 抓取——WT/fallback 共用同一张证书，指纹一致）；完整操作指南见 [手册.md](手册.md#pin-指纹获取与轮换)；
    * **pin 的是握手对端的证书**：档位 1（nginx 终止 TLS）下 pin nginx 的证书，不是 newppp 的；
    * **轮换即失效**：换证书（LE 续期/重签）后指纹变化，客户端全部拒绝（报 `certificate fingerprint mismatch (--pin)`）——`--pin` 的预期组合是自签/长有效期证书（证书静态、指纹静态），LE 自动续期部署不要用 `--pin` 也不要用 `--sni`（伪装与 LE 证书互斥）；
    * 轮换操作顺序：服务器换证书 → 重算指纹 → 更新客户端配置 `pin = ...` → 重启客户端（降级链平滑迁移）。
  - 验收：
    * 单测：`--sni`/`--pin` 参数解析、互斥校验、指纹格式校验（hex 64 字符）；✅ 已落地（config ×7 + PinVerifier ×2）；
    * e2e：真实 WT 连接 + `--pin`（对自签服务端 pin 指纹）→ 连接成功；错误指纹 → 连接拒绝；✅ 已落地（`sni_masquerade_with_pin_connects` / `sni_masquerade_wrong_pin_rejected`）；
    * `--sni` 设定后抓包断言 ClientHello SNI == 伪装域名（部署后人工核验）；
    * e2e 全绿（缺省路径零回归）。✅
  - 状态：**✅ 已落地（2026-09-14）**——87 lib + 13 e2e 全绿，服务端零改动。
  - 债：D5（SNI/DNS 明文暴露）——本项直接关闭直连路径的域名泄露；DoH（DNS 面收口）降级为 Backlog（`--doh` 仍值得做但不再是 ECH 前置依赖）。
  - 定级依据：约 F-5 量级代码 + 服务端零改动 + 直连路径域名泄露直接归零；运维前提仅"选一个伪装域名"，无 DNS 提供商/CF 配合要求。

### 暂不做（写下来防止摇摆）

- **ChromeParrot 等效物（完整 ClientHello 伪装）**：需同时 fork quinn-proto + rustls 两层并逐字节重写握手——维护负担随上游升级无限累积。Hysteria 能做是因为 quic-go 自带 TLS 握手（fork 一层即可）；Rust 分层架构无此条件。**除非出现"走 CF 后仍被指纹识别封端口"的真实事件，否则不立项。**F-2 探明的 TP 结构性残留（min_ack_delay / grease TP / write_order / ack_delay_exponent）同属此路径，一并归入。
- **Salamander / Gecko 式 UDP 层混淆**：**已探明不可行**（2026-09-14）——wtransport/quinn 的 socket I/O 循环由 runtime 层内部持有（`Endpoint::new` 直接接管 UdpSocket），仅支持传入 socket 本身（`with_bind_socket`），**不支持逐包变换**（Salamander 的 XOR 混淆、Gecko 的握手分片都要求在协议栈之下改写每个 UDP 包）。等效实现必须 fork quinn 的 transport runtime。且 Salamander 与"过 CDN"主形态冲突。
- **换 quinn+h3 栈实现 GET/WT 同端口共宿**：沿用上版暂缓项结论（触发条件：主动探测导致节点被封）。

## 明确的"不做"（写下来防止以后摇摆）

- **不加 Alt-Svc**：UDP 443 现在不应答网页请求，广播 Alt-Svc 等于邀请浏览器来探测一个答不上话的端口。
- **不做多级 fallback**：WT→POST/WS 已覆盖全部三种部署形态。
- **不做 per-user ACL/配额/计费**：`--auth` 多用户 + 连接级限速对"少量可信用户"够用。
- **不做自适应调参**（recv-window/conns 自动调优）：调参经验写进 [运维手册.md](运维手册.md)。
- **不拆 crate/微服务**：目录边界已清楚，`lib.rs` 已支撑集成测试。
- **不 fork quinn/rustls 做 ClientHello 伪装**：见上「暂不做」。
- **不做 uTLS 式 TLS 指纹库移植**：Rust 生态无维护良好的等效物，自研投入产出比极差。
