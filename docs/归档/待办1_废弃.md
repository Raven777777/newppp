### 观察项（先基准后动，避免过早优化）

- **限速器唤醒模型**：令牌桶不足时 sleep 循环重试，大缺口唤醒偏多；换带 waker 的异步令牌桶。
- **UDP relay 套接字池**：每 UDP 会话每族新 bind，DNS 密集场景 churn 明显；现状 128 socket/连接上限可接受，视需要再做。
- **池并发超额 dial**：`WtPool::acquire` 在并发下可能同时拨出多条连接、短暂超过池目标规模（维护循环随后裁剪）；高峰期只是瞬时资源波动，出现实际浪费再做 dial 去重。
- **fallback ensure_mux 并发重建**：mux 死亡瞬间多个请求可能各建一条新通道（旧 `MuxClient` 被 `Mutex<Option>` 覆盖后阻塞排空）；影响小，若日志出现频繁重建再加单飞（single-flight）。
- **ReplayWindow 烧帧**：合法但损坏的数据报在解密失败前已占用滑动窗口位（AEAD 前置校验的标准权衡）；若高丢包 UDP 链路出现回复异常丢包，考虑"解密失败回滚窗口标记"。

### 排查中：WT 连接频繁重建（服务端 `wt conn authenticated` 每 2~6 分钟成对出现）

**现象**（2026-09-12 12:14~12:32 服务端日志）：INFO `wt conn authenticated uid=2233` 反复出现，多为相隔 0.5~1.5s 的成对记录，间隔 2~6 分钟不等。**已确认属"连接死亡后客户端重建"**，不是重复认证：

- 成对 = 客户端默认 `--conns 2`，池维护任务 `spawn_maintenance` 顺序重拨 2 条（`any_ok=true` 重置退避为 10s 起步，故重拨保持密集）；
- 每次重拨均为新 bearer + 新 nonce，安全/配额层面无副作用，仅连接 churn 指标差；
- 待确认的是**旧连接为何频繁死亡**：候选 ① 服务端 reaper（`--idle 60`，无会话且无数据活动 > 3×idle = 180s 即主动关闭，设计行为）；② `--recv-window` 过大 + 丢包链路触发 quinn "too many gaps" 整连接 abort（README 已知限制，恰好是多分钟一次的形态）；③ 握手超时（`open_bi timeout` 等，任一超时即标记整条连接 dead）；④ NAT/QoS 干扰 UDP。

**判据**（不改代码，两端 `--log debug` 即可收敛）：

1. 服务端搜 `reaping idle conn` → 命中即候选 ①（需调大 `--idle`）；连续日志期间无 reaping → 转 2；
2. 客户端搜 `wt connect failed` / `open_bi timeout` / `stream open timeout` / `pool maintenance connect failed` → 命中即候选 ③（链路质量）；
3. 客户端搜 `wt datagram: bad frame`——行本身无害（`dec.clear()` 恢复设计），但**频繁出现 = datagram 通路脏/丢包**，指向候选 ②④；
4. 试 `--recv-window 1` 观察重拨间隔：明显拉长即确认候选 ②，可长期用小窗口值；
5. 收敛后视结论决定：改默认 `--idle`、默认 `--recv-window`（连接死亡原因日志已随 P0 Pong 判死落地——客户端日志 `wt connection dead: <原因>`）。

### 暂缓项（大工程，单独立项）

- **同端口 H3/WT 伪装一体化**：同一 UDP 443 既能响应标准 H3 GET 静态网页（发 Alt-Svc），又能升级 WebTransport，补齐 QUIC 层探测漏洞。现状：UDP 443 不应答 h3 GET、不发 Alt-Svc，定制探测可发现"这个 QUIC 服务不是网页"。根治需把 wtransport 换成 quinn + h3 栈（传输层重构、伪装页走 h3、认证流程不变；两端都是自有客户端，无第三方互操作硬需求）；启动前先抽传输抽象层 + 钉死现有行为基准。
- **QUIC/TLS 指纹混淆**：进一步调优 quinn/wtransport 的 `TransportConfig`（初始/流控窗口、`max_idle_timeout`、ACK 策略、连接迁移、`active_connection_id_limit`、`max_udp_payload_size` 等），并人工拟合 Chrome 的 ClientHello 结构（扩展集合与顺序、GREASE、key_share/密码套件、ALPN、SNI 形态），降低主动/被动 DPI 的特征识别率（JA4/QUIC 指纹）。现状：quinn 指纹≠Chrome（README「已知限制」），被动分类无特征但主动探测可辨。难点：wtransport 封装了部分 TLS/传输配置、rustls 与 Chrome 的 ClientHello 存在结构性差异、Chrome 版本漂移需持续跟踪；改动限定在客户端出站配置，不破坏服务端互操作。启动前先建指纹采集/比对基线（如 `ja4`/`p0f` 类工具对两端握手抓包），再逐项拟合。
- **Argon2 慢哈希密码 KDF**：密码爆破是体系真正弱根，但属**协议 v2 破坏性改动**（需版本协商与两端同步升级）。
- 模式 A 单通道队头阻塞：架构固有，WT 主路径已覆盖大多数场景。

### 新增功能候选（按需求热度排期）

- **空闲降载：无会话空闲拆除 WT 连接、按需重拨**（已选定方案，针对"客户端 24/7 待机时 15s QUIC keepalive + 30s 应用 Ping 的恒定心跳信标"问题）：
  * **动机/解决面**：待机期变为零包——消除"间隔 30s 的规律小包打到固定 IP"这一教科书式 beaconing 指纹（被动观测者视角）；顺带消除服务端 reaper 的 3 分钟一轮"回收→重拨→认证"churn（连接不存在就不会被回收复位），服务器侧无谓资源占用下降；
  * **设计**：连接满足"无会话 + 最近一次**非心跳**数据活动超阈值"→ 池维护任务主动 `close()` 并置 `alive=false`（与 reaper 同类语义；服务器 keepalive 不计入活性的现成就是拆判定依据）；SOCKS5/HTTP 入站**照常监听不动**，`WtPool::acquire()` 本就支持池空现场 dial，新会话到来自动重建（无新模块，只改 maintenance 的"无条件补活"为"超拆判定"）；
  * **CLI**：新增 `--idle-disconnect <secs>`（0 = 关闭，保持现行常驻行为，向后兼容；默认建议 0，愿意用的用户显式开启）；
  * **代价/残余（须写进 README 隐私模型小节）**：① 冷启动首请求多付一次完整握手（QUIC+TLS 约 2~3s），弱网下首请求可能触发降级链；② 使用期流量与时序元数据照旧；③ 重建突发与使用行为对齐——属"把均匀信标换成与使用内容相关的真实网络行为"，识别性大降但非零；
  * **实现提示**：阈值计时直接复用 `ConnState.last_active` 同源思路（客户端侧需给 `WtConn` 加等价的"最近非心跳活动"戳，Pong/keepalive 不刷新之）；拆除瞬间的日志与既有"池维护 retire 冗余连接"逻辑合一，避免双路径。
- **SOCKS5 TODAY/只读分流规则**（本地 PAC/规则文件）：域名/网段分流直连与代理，提升本地客户端可用性；改动仅在入站侧，协议无感。
- **每用户会话/流量统计持久化**：配合 `/metrics` 落盘（时间轮转 JSON），多用户计费/审计基础。
- **热更新凭据**：SIGHUP 或配置文件 watch 重新加载 `--auth` 用户表，不重启增删用户（依赖"配置文件支持"先行）。
- **客户端系统代理一键配置**（可选 GUI/脚本）：写 Windows/注册表、macOS networksetup——部署体验加分项，非核心。
